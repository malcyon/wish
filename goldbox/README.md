# goldbox

The game's formats, decoded — character records, save games, maps, items,
spells. No Qt, no emulator, no transport: everything here is bytes in and bytes
out, so it can be driven from a `.D64`, from a live memory read, or from a
test's own array.

| file | purpose |
|---|---|
| `__init__.py` | Empty. |
| `amiga.py` | Amiga *Pools of Darkness* `Save/NAME.pc` character files, big-endian, and the writer that turns a `NeutralCharacter` into one. Every offset was read off the screen by writing probe payloads onto a copy of disk 3; the record holds base values only, because the game rederives THAC0, encumbrance and movement on load. Also the Amiga *Pool of Radiance* character, item and effect files -- not a second field table: each reads the DOS one in `dos_layout.py` through a shift map, big-endian, so the two cannot drift apart. `to_neutral` re-cuts the 288-byte record into the 285-byte DOS one and hands it to `dos.to_neutral`, which is the Amiga reader of `neutral.py`'s set, and `write_por` runs the same transposition backwards over `dos.write`'s output, which is the writer. `to_neutral` names every `.spc` effect the neutral record cannot hold -- three of the twenty specimens carry an item-granted one, and until `#232` gives it a field the writer emits no node for it, so the least it can do is say which effect went and whether it had a duration. `write_por_slot` puts a whole slot on a disk -- the six characters, their item and effect files, the saved game, and `SAVE/save`, the ten bytes the picker reads -- an array indexed by the slot letter rather than a list, `A` at byte 0 and `J` at byte 9, measured by making the game save to `D` and then to `B` and reading back `"AB D      "` -- and **refuses a slot it cannot list**, because a slot the game will not offer is one the player cannot load. The write is all or nothing: it snapshots the disk first and rolls back on any failure, since a half-written slot is a corrupt disk. Also **Amiga Curse of the Azure Bonds and Secret of the Silver Blades** (`#55`), as `AmigaShape` rows rather than as code: each is a shift map onto its own title's `dos_layout.py` shape, so a third port is data. `AmigaCharacter` reads either, `AmigaItem` reads Curse's 66-byte item node, `read_amiga_guy` reads a `.guy` pregen and `party_in_savegame` finds a party inside a saved game by signature rather than by a table nobody has decoded yet. The Silver Blades map is checked against its own DOS twin -- both ports ship the same six characters -- and Silver Blades alone packs its spellbook into 15 bytes of bitmask where DOS spends 117. Three windows in Curse hold an insertion nobody has located and `get` **raises** for a field that touches one, rather than handing back a byte from the wrong side of it. |
| `amiga_adf.py` | The Amiga floppy filesystem (OFS), read **and written** — allocate blocks from the bitmap, build a file header, thread it into the parent drawer's hash chain, fix every checksum. Enough to hand a player a real game disk with their party on it, which overwriting a file's bytes in place could never do. Every structure was measured against the player's own disks first, and the allocator counts down from the top of the disk because a cracked release reads blocks the bitmap calls free. `make_dir` is there for the tests rather than for production -- it is what lets a save slot be written onto a disk this module formatted, with no game data anywhere -- and `restore` puts a whole image back to a snapshot, so a caller writing sixteen files at once can undo a run that stopped half way. `walk_dirs` is what lets `verify()` reach a drawer's own header block, which it could not before -- until then every directory this module wrote was the root, so a drawer with a wrong checksum verified clean. |
| `areas.py` | The single source of truth for the thirty Pool of Radiance areas, keyed by **area id** rather than by map file — `ECL0C` does not exist, and four areas never put a `GEO` on the screen at all -- thirty areas, twenty-nine maps, which is the count `docs/88-map-files.md` inventories. |
| `c64_codec.py` | The C64 codec: a `NeutralCharacter` becomes 580 C64 bytes and back again. Every byte written is justified as sourced, computed by a named rule, or a documented constant; the reader takes the roster block and the item page separately, because a save slot holds only 256 of the 580. |
| `commissions.py` | The City Council's reward ledger, offer board and summons, read out of the 224 persistent flag bytes at `$4A20`, and the side quests an area script keeps for itself. No transport, so it works from a save file or a live read alike. |
| `d64.py` | Commodore 1541 `.D64` reader and writer, including **building a disk from nothing** (#118) -- `blank()` formats a 35-track image with a valid BAM and an empty directory, and `write_file` allocates blocks, writes the sector chain and links a directory entry, growing the directory chain past eight entries. The BAM layout, the interleave and the track order were all read off the player's own fifteen save disks, and writing a real save's two files onto a blank built here reproduces the disk the drive wrote everywhere but the slack in each file's last sector. A file is never grown or replaced: `write_file_inplace` rewrites one over its existing chain at the same block count, and nothing scratches a file, so no block is ever freed. |
| `derive.py` | Recomputes armour class, THAC0 and the damage bonus from the AD&D rules so a value the game cached and never refreshed can be reported as stale. Writes nothing. |
| `dos.py` | The DOS Gold Box codec. **Reads all four titles** — Pool of Radiance, Curse, Silver Blades and Pools of Darkness — because the record's own length names the title; **converts only Pool of Radiance**, which is the one pair of ports measured against each other, and raises `WrongTitleError` for the rest. Both directions for that one: reads a DOS save into the neutral record, and since #26 writes one back — the record, its `.ITM`, and a whole save over a template's `SAVGAM`. In the DOS→C64 direction **there is no template at all** (#118): `new_save` writes every one of the 9216 bytes of `SAVEDGAME0` and `SAVEDGAME1` and `save_disk` puts them on a blank `.d64`, so the caller has to supply the two things that are the game's own data — the composed combat icon and `ANIMATE00` — off the player's disks. A field with no home on the other side is *reported* rather than dropped silently. |
| `dos_layout.py` | The DOS character record as the same declarative `Field` / `Confidence` table `layout.py` uses: Pool of Radiance's 285 bytes measured against 24 real specimens, and the other three titles as **one `DosShape` row each** — a set of width overrides against that table, from which `layout_for` accumulates the offsets. A width that is wrong stops the record adding up to its own size and raises at import. Both directions of `dos.py` read it; the player's own files are never written to. |
| `dos_savegame.py` | The DOS `SAVGAM?.DAT` saved game mapped (#59, #60): the VM word array indexed by ECL address, the clock, the party size, the wallset triple and the live ECL script buffer — accessors over any save's bytes, the writers that move a save to a new area (`retarget`, `RETARGET_WRITES`), and the `.DAX` container reader both this package and `tools/dosbox.py` use — index, run-length decode and refusals, one copy (#76). Also **one `DosSaveShape` row per title** (#53): the container as region widths that have to add up to the size the file is, so a fifth title costs a row rather than a branch. Curse and Silver Blades share Pool of Radiance's variable array offset for offset, Silver Blades stages no script at all, and Pools of Darkness writes a `SAVGAM?.PTY` whose first 1024 bytes nobody has decoded. |
| `effects.py` | The 64-slot active-effect arrays at `SAVEDGAME0` `$4900` -- owned by a character, a monster or the party, and distinct from the ten trait slots at record `0x0AD` -- plus `load_effect_table`, ECL65's own 67-record spell-effect table relocated to `$9900`, read off a game disk for a new effect's duration. Ported out of `automap/live.py` on `#13 (Edit traits and active effects, in two separate panels)` so the editor's panels can reach it without importing `automap`. |
| `encoding.py` | The three biased fields in one place — THAC0 and armour class stored as `60 - value`, the armour bonus as `48 + value`. Functions rather than a constant to subtract by hand, because every caller that forgot was off by a lot and in the wrong direction. |
| `games.py` | Which Gold Box title a save came from, as a table of numbers rather than a class hierarchy. Six C64 titles share one engine and one 580-byte record; what differs is the file names, the load addresses, whether the roster is a second file, and the race and class tables every codec resolves an index through. |
| `geo.py` | The GEO map format: four 256-byte planes over a 16x16 grid, with wall art and passability as two **independent** fields — conflating them is what made five earlier readings of GEO fail. |
| `iconparts.py` | The icons the game can actually *make* — a weapon and a head, chosen in pairs by size — read out of the `SPELLE64` / `SPELLN64` icon editor, as against the 10^43 an 18-cell free choice would offer. `default_icon()` composes the one the game's own character creation writes, which is what a conversion from a port with no C64 icon puts in a save. |
| `icons.py` | The eight 36-byte combat icons at `$4BE0` in `SAVEDGAME0`: 18 screen codes then 18 colours, established by diffing in-game icon edits. |
| `items.py` | Inventory — the sixteen 16-byte item records per character at `$5900 + slot * $100`, and the word table the game assembles item names from. Weights are in tenths of a pound. |
| `layout.py` | The 580-byte C64 character record as a declarative table of fields, each with a confidence grade. Nothing else in the project may hard-code an offset; bytes no entry claims become UNKNOWN regions at import time, so overlaps and gaps are impossible to introduce silently. Its field notes are **generated** into `docs/20-character-record.md` by `tools/gendocs.py`. |
| `levels.py` | Experience thresholds, saving throws, turning and spell progression, per title — read off the player's own disks and cross-checked against AD&D 1st edition rather than taken from either alone. |
| `levelup.py` | Reproduces, field by field, what the training hall writes at a level-up, with each step traced to the `GEN` routine that performs it. |
| `memory.py` | The game's memory map *outside* a character record — party header, loader caches, combat tables — as a purely descriptive table with confidences, so "what is at `$4BC2`" stops being a grep. **Generates** `docs/41-memory-regions.md` via `tools/genmemory.py`. |
| `monster.py` | The two attack forms and the experience award, read off any 580-byte record — a goblin and a level-1 fighter are the same structure. Reads `0x0D9`–`0x0E0` and never the working copies at `0x111`. |
| `neutral.py` | The port-neutral character record every conversion passes through, where each value carries its provenance and not just a number, plus the `Writer` every writer inherits the take-refuse-report protocol from. A codec per format around one record instead of a converter per pair. |
| `petscii.py` | C64 text, keeping the two string conventions apart: NUL-padded ASCII inside a character record, shifted-space-padded PETSCII in a 1541 directory entry. |
| `portraits.py` | The character sheet's portrait, and the one enumeration the C64 and DOS ports share: fourteen heads and twelve bodies, whose art ids are the same numbers on both sides — the C64's `HEAD2D` file is DOS's block 45 of `HEAD3.DAX`. The C64 record stores the id and DOS stores the menu position, so a conversion needs the menu, and the menu is a table in the player's own files on both sides. Nothing is hardcoded: `tables_from_dos` finds it in `START.EXE` and `tables_from_c64` in `GEN` on `POOL3`, by the shape of the run and by checking every value names art that is actually there. |
| `record.py` | `CharacterRecord` — bytes in, bytes out, with every field read and written *through* `layout.py`. That makes a decode/encode cycle byte-exact by construction, so the bytes whose meaning is still unknown can never be dropped or zeroed in passing. |
| `savegame.py` | The save container in both its shapes: Pool of Radiance's two files (`SAVEDGAME0`, a raw `$4900`–`$64FF` memory image, plus `SAVEDGAME1`), and the single 7426-byte file every later title writes. |
| `spells.py` | The spell name table per title, and what the packed list of spell ids at record offset `0x020` means. The names live on the game disk, and *where* is the one thing that does not transfer between titles. |
| `strength.py` | Recomputes PARTYSTRENGTH, the number twelve area scripts size random encounters from. Nothing stores it, so this walks the roster the way `DUNGEON $1BE8` does — using the biased THAC0 and armour class bytes as stored, not as decoded. |
| `traits.py` | The ten trait slots at `0x0AD` — racial abilities, monster specials, item powers — as a 1–139 namespace per title, 66 entries confirmed against the player's own disks. Pool of Radiance's is the DOS port's too and Curse shares it; Silver Blades reassigned the numbers and carries its own, smaller, table. |
| `world.py` | `SQRDATA0n`, the overland travel map -- the combat square engine's own shape (`automap/combat.py`) pointed at the wilderness instead of an arena: the 18x36 grid, the 120 tile glyphs, and the three files stitched at world x 15 and 28 in the game's own coordinate (`x + 13 * window_index`). `passable()` and `site_at()` are named but **not implemented**: the site and impassable-terrain tables live in `ECL19`/`ECL1A`/`ECL1B`'s bytecode, whose addresses were lost with `work/reports/world-map.md`, and recovering them means reopening the ECL-script reading `docs/115-review-the-scripts.md` closed at Donald's own direction. |
| `yaml_io.py` | The YAML codec: writes a `NeutralCharacter` out as plain data and imports a document back into a save, losslessly. Only understood fields are editable, and the header, the roster tail and the majority of each record still unidentified are carried through byte for byte. |
