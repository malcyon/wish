# Making `tools/d6502.py` trustworthy

**Status: plan.** This is the work list for putting `tools/d6502.py` — the
small 6502 disassembler whose listings produced `docs/147-combat-rolls.md` —
under test, after `tools/m68dis.py`'s first draft showed what an untested
disassembler does: it decoded the letters `ER` as a real instruction, and only
a cross-check against an independent decoder caught it (#148, "The Amiga
port's tools are gone, and phase 1 still needs the disassembler").

Written 2026-09-01, from a read of the code and a first capstone sweep run
during planning. **The sweep already found a real bug** — see "What is known".

---

## What "trustworthy" means here

Four properties, in order of importance:

1. **Every opcode it knows is decoded correctly** — mnemonic, size and
   addressing mode all right. This is the property that is currently violated
   (`$F6`, below).
2. **An opcode it does not know prints as `.byte $xx`**, never as the nearest
   instruction that fits. The current code already does this: `run()` prints
   `.byte` and advances one byte for anything absent from its table, and the
   table holds exactly the 151 documented opcodes — all 105 undocumented ones
   refuse. Keep it that way; do not add undocumented-opcode decoding.
3. **Nothing is silently misrepresented at the edges**: a branch target wraps
   at `$FFFF` the way the CPU does, an instruction cut off by the end of the
   image prints its bytes as `.byte` rather than vanishing, and a start
   address outside the image says so instead of printing nothing.
4. **An honest limit, stated rather than hidden:** on a 6502 a string decodes
   as plausible instructions and no decoder can prevent it. 151 of 256 byte
   values are legal opcodes with no reserved fields to check, so — unlike the
   68000, where `m68dis.py` can refuse `$4552` — PETSCII text here *will*
   come out as `EOR`s and `AND`s that decode correctly. The guarantee this
   tool can make is "every printed instruction is the true decode of those
   bytes", not "these bytes are code". That sentence goes into the module
   docstring so nobody cites a listing of a string table as code.

## What is known

* **CONFIRMED — `$F6` is decoded wrongly.** Line 27 of the opcode table reads
  `F5 SBC ZPX;F6 SBC ZPX`: a copy-slip duplicate. On a real 6502, `$F5` is
  `SBC $nn,X` and `$F6` is `INC $nn,X`. So every `INC $nn,X` in an overlay
  prints as `SBC $nn,X`, and `$F5` and `$F6` print identical text, so the two
  cannot be told apart in a listing. Found 2026-09-01 by sweeping all 256
  opcodes against capstone (method below).
* **CONFIRMED — capstone in `.venv` decodes 6502.** capstone 5.0.7 is
  installed (deliberately outside `pyproject.toml` and the test suite) and
  supports `CS_ARCH_MOS65XX` with `CS_MODE_MOS65XX_6502`. Verified working on
  this machine.
* **CONFIRMED — the sweep of all 256 single opcodes found exactly 2
  disagreements**: `$F6` (the real bug) and `$00` (capstone counts BRK's
  signature byte and reports size 2; d6502 prints size 1, which is what most
  6502 listings do — a convention difference, declared as an exception below,
  not a bug).
* **CONFIRMED — presence agrees on all 256 opcodes**: every opcode d6502
  refuses, capstone's 6502 mode also refuses, and vice versa.
* **PROBABLE — no instruction quoted in `docs/147-combat-rolls.md` is
  affected.** Every quoted line there is immediate, absolute or a branch
  (`CMP #$01`, `BEQ $12AF`, `SBC $6C19` — absolute, opcode `$ED`, not the
  buggy `$F6`), none is `zp,X`. But the *listings* the doc was derived from
  are gone with `work/rolls/`, so whether a misprinted `INC $nn,X` sat inside
  a routine somebody reasoned about has not been checked. Step 7 settles it.
* **UNKNOWN — whether the player's disks are present on the machine that runs
  step 6.** If not, that step is reported as not run, and the synthetic sweep
  (step 5) is the evidence.

## Decisions already made (do not re-decide these)

* `.byte` for unknown opcodes stays. BRK stays 1 byte. Undocumented opcodes
  stay refused.
* The committed tests use **hand-built bytes only** — no capstone, no game
  data, no skips. `CLAUDE.md` forbids committing the game's code, and
  `tests/test_repository_contents.py` fails the build on it; and a suite that
  is green because tests skipped has told nobody anything. capstone stays out
  of the suite (the `m68dis.py` precedent: its 100 385-instruction capstone
  check was a one-off experiment, and `tests/test_m68dis.py` builds every
  case by hand from the manual). A disk-backed test *without* capstone would
  only compare d6502 with itself, so there is no disk-backed test at all.
* The tool does not grow features. No `--refs`, no dataclass API, no
  undocumented opcodes. It needs to be trustworthy at what it does.

### Step 1 — make the output testable

`run()` only prints, so nothing can assert on it. Extract a function:

```python
def lines(data: bytes, base: int, start: int, count: int) -> list[str]
```

returning exactly the strings `run()` prints today, and have `run()` read the
file and print them. Mechanical: no output change of any kind.

**Done when:** running the tool on a scratch file of `bytes(range(256))`
before and after the change produces byte-identical output (`diff` the two
captures; keep them under `work/d6502-plan/`). Note: after copying a file
aside and back for any before/after check, delete `__pycache__` —
`CLAUDE.md` explains why.

### Step 2 — fix `$F6`, regression test first

Create `tests/test_d6502.py` (model: `tests/test_m68dis.py` — a short helper
that builds bytes by hand and returns the disassembled text). First test:
`bytes([0xF6, 0x20])` disassembles as `INC $20,X`. **Run it and watch it fail
with `SBC $20,X`** — a regression test that has never been red is a guess.
Then change the table entry `F6 SBC ZPX` to `F6 INC ZPX` and watch it pass.
Add the neighbour in the same breath: `bytes([0xF5, 0x20])` is `SBC $20,X`.

**Done when:** both tests pass, and the first was seen red before the fix.

### Step 3 — the hand-built suite

Every case is assembled by hand from a published 6502 reference (the MOS
MCS6500 manual's opcode table, or any independent source — not from
d6502's own table, which would restate the implementation). The list:

* **One case per addressing mode**, all 13:
  implied (`EA` → `NOP`), accumulator (`0A` → `ASL A`), immediate
  (`A9 41` → `LDA #$41`), zero page (`A5 20`), zp,X (`B5 20`), zp,Y
  (`B6 20` → `LDX $20,Y`), absolute (`AD 34 12` → `LDA $1234`), abs,X
  (`BD 34 12`), abs,Y (`B9 34 12`), indirect (`6C 34 12` → `JMP ($1234)`),
  (zp,X) (`A1 20` → `LDA ($20,X)`), (zp),Y (`B1 20` → `LDA ($20),Y`),
  relative (`D0 FE` at `$1000` → `BNE $1000`).
* **Branch arithmetic**, the commonest thing to get wrong: a forward branch
  (`+$7F`, the largest), a backward branch (`-$80`, the largest), a branch
  whose target crosses a page boundary (page crossing changes cycle counts,
  not targets — the test pins that the target is plain arithmetic), and the
  two wrap cases from step 4.
* **An unknown opcode resynchronises by one byte**: `bytes([0x02, 0xA9, 0x41])`
  produces `.byte $02` then `LDA #$41` — three bytes, two lines.
* **A run of illegal opcodes is all data**: `bytes([0x02, 0x22, 0xFF])` is
  three `.byte` lines.
* **BRK is one byte**, with a comment naming the declared capstone
  disagreement: capstone counts the signature byte (size 2); most listings
  and this tool do not.
* **The `$FFFF` wrap and truncated-tail cases** — written in step 4, where
  their fixes are.

**Done when:** every test passes, `pytest tests/test_d6502.py` runs with zero
skips, and no test imports capstone or reads a file.

### Step 4 — the three edge fixes, each test-first

Each of these is red before its fix, by design; watch each fail before
changing the tool.

* **Branch targets wrap at `$FFFF`.** `fmt()` computes `pc + 2 + off` unmasked,
  so a branch near the top of memory prints a five-digit target and a
  backward branch near `$0000` prints garbage. Mask with `& 0xFFFF`. Tests: a
  forward branch at `$FFFC` whose target wraps past `$FFFF`, and a backward
  branch at `$0000`.
* **A truncated instruction prints its bytes.** Today `run()` silently
  `break`s when the image ends mid-instruction, so the listing just stops
  short of `count` with no sign anything was there. Print each leftover byte
  as `.byte $xx` instead — consistent with the unknown-opcode path, and the
  same choice `m68dis.py` made (`dc.w` at a window edge). Test: an image
  ending with `AD 34` (absolute `LDA` missing its high byte) produces two
  `.byte` lines, not silence.
* **A start address outside the image says so.** Today it prints nothing at
  all. One line to stderr — `d6502.py: $XXXX is outside the image` — and
  stop. This is CLI diagnostics, not GUI text, so it does not need Donald's
  wording approval; keep it to one line.

**Done when:** all three were seen red, then green, and step 1's
`bytes(range(256))` capture is regenerated and eyeballed — the only expected
differences from step 1's capture are the `$F6` line and the tail.

### Step 5 — the synthetic capstone sweep, re-run and recorded

A one-off experiment, not a test. Script lives in `work/d6502-plan/`
(gitignored); its method is recorded here so it can be rewritten from this
paragraph if lost.

Method: for each opcode `$00`–`$FF`, build `bytes([op, 0x34, 0x12])`, decode
with `capstone.Cs(CS_ARCH_MOS65XX, CS_MODE_MOS65XX_6502)` and with
`d6502.T`/`SZ`/`fmt`, and compare **presence** (both decode, or both refuse)
and **(mnemonic uppercased, size)**. Do not compare operand text — capstone
prints `(0x20), y` where d6502 prints `($20),Y`, and capstone's accumulator
operand is the letter `a`, which a hex-token extractor reads as the number 10.
Feed capstone one instruction at a time: its `disasm` stops at the first
illegal byte, so a multi-instruction buffer under-reports.

**Done when:** the sweep reports **exactly one** disagreement — `$00`, the
declared BRK size exception — and the count, the date and the capstone
version are recorded in a "Results" section appended to this document and in
a comment on the issue tracking this work. Any other disagreement: stop and
report; do not change d6502 to match capstone without checking a published
opcode table first, because either side could be the wrong one.

### Step 6 — the real-bytes sweep, if the disks are present

The synthetic sweep covers one operand pattern per opcode; real overlays
cover the rest and are what the tool is actually pointed at. Same script
family, same home in `work/d6502-plan/`.

Method: load `COMBAT` and `LIBRARY` off the player's disks the way
`tests/gamedata.py` does — `automap.paths.find_disks()` to locate them,
`goldbox.d64.load_payload(disk, b"COMBAT")` to read (open the disks
read-only; never write to that directory). `docs/147-combat-rolls.md` says
`COMBAT` loads at `$0800` and `LIBRARY` at `$2C48`; check whether the
payload's first two bytes are that address little-endian (the C64 PRG
convention) and skip them if so. Then walk each file end to end: at each
position, take up to 3 bytes, decode with both, compare presence and
(mnemonic, size) exactly as in step 5, advance by **d6502's** size (1 for a
`.byte`), and treat `$00` under the declared BRK exception — d6502 advances
1, and capstone is simply asked again at the new position, so nothing
cascades. Both decoders are context-free, so comparing across data regions is
as valid as across code.

**Done when:** the script reports how many positions were compared and every
disagreement, and the answer is zero outside the BRK exception — recorded in
the Results section and the issue comment with the counts ("N of N agree" is
evidence; "it ran fine" is not). If the disks are absent, say so in those
words and move on; step 5 remains the evidence.

### Step 7 — check whether the `$F6` bug touched `docs/147-combat-rolls.md`

The original listings are gone with `work/rolls/`, so regenerate: run the
fixed tool over `COMBAT` from `$0800` and `LIBRARY` from `$2C48` (same disk
loading as step 6) and search the output for `INC $` lines with `,X` — each
one printed as `SBC $nn,X` in the listings the doc was written from. For each
hit, say whether its address falls inside a routine the doc cites: around
`$11AC`–`$12E3`, `$0CFE`–`$0D10`, `$2B10`, `$2D88`–`$2DEC`, `$35CB`–`$35CE`
in `COMBAT`/`LIBRARY` terms. The listing itself stays in `work/` and is never
committed; only the addresses of hits are reported.

**Done when:** the answer — including "no hits in any cited range", if that is
the answer — is in a comment on the issue. **If a hit lands inside a cited
range, stop there**: whether `docs/147-combat-rolls.md` needs re-examination
is Donald's call, not this task's. Do not edit that document either way.

All eight steps done. `tests/test_d6502.py` has 25 cases, zero skips, no
capstone import, no game bytes.

* **`$F6` was seen printing `SBC $20,X` for `bytes([0xF6, 0x20])`** before the
  table fix, confirming the regression test was red for the right reason
  (`docs/148-d6502.md`'s own "What is known" already established the mechanism
  -- this is the test proving it). Fixed to `INC ZPX`; `$F5` unaffected.
* **The three edge fixes were each seen red before their fix**: the branch-wrap
  tests failed with unmasked five-digit targets (`BNE $1007D` instead of
  `$007D`), the truncated-tail test returned no lines at all for `AD 34` at the
  end of an image, and the out-of-range-start test found no stderr message.
* **Synthetic sweep (step 5), capstone 5.0.7, 256 opcodes**: exactly one
  disagreement, `$00` (BRK size 1 here, 2 in capstone) -- the declared
  exception. Method and script: `tools/d6502check.py`, which reruns both
  this sweep and the real-bytes one below. **It reports fewer positions than
  the counts below** -- 3863 and 3278 against 4063 and 3468 -- because it
  leaves `$00` out of the comparison rather than counting the disagreement it
