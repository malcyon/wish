# amiga

Scripts for the Amiga ports: reading their disk images and executables, disassembling them, and driving them under FS-UAE and WinUAE.

| file | purpose |
|---|---|
| `amiga68k.py` | Reads a Gold Box Amiga executable: lists its hunks, finds who references a file offset, and disassembles a range with SAS/Lattice `jsr d16(a4)` jump-table calls and `RELOC32` absolute operands resolved and C strings quoted. Needs `capstone`. This is how `docs/165-amiga-savegame.md` was read. |
| `amigabladesjournal.py` | Answers Amiga *Secret of the Silver Blades*'s journal prompt, which is what stood between an agent and a driven Silver Blades session, and records nothing about it (`#331 (Amiga Silver Blades asks a journal word before it will adventure, so the title cannot be driven past its party menu)`). The question names a printed Adventurer's Journal and the words are on the disk: the arithmetic that gets them out is copy-protection research and `CLAUDE.md` keeps it in Donald's separate private repository, so this reaches into that repository at run time -- `$WISH_CODEWHEEL`, or the `codewheel` entry in `gamedisks.yaml` -- reads the challenge off the guest's screen with its reader, matches it against tables that repository extracts from the player's own side-A disk, types the word and RETURN through `amigadrive.py`, and deletes the screenshot. What it prints is `answered` or `no challenge on screen` and never the challenge or the word; a challenge the tables do not hold is refused without quoting either side, because the matcher's own exception message quotes it. The geometry is what had to be worked out here: that reader was written against FS-UAE, where the game's 8x8 character cell is 30.64 captured pixels, and `winvm shot` grabs a 1920x1080 desktop where the same cell is 16 -- so the grid is fitted from the challenge's own inked rows, and the fitted origin is handed to the reader in place of its own. One screen's `6` used to read as an `8` (`#371 (The Silver Blades journal reader misreads a 6 as an 8, so a boot is spent on a question the disk can answer)`), because the reader's declared 30.64 is 3.83 pixels for each of the 8 in a cell, so building its image replicated some of the game's own pixels four times and others three, and a one-pixel gap that comes out three wide beside one that comes out four does not survive the reader's normalise-to-8x8. It now samples each Amiga pixel's own centre out of the untouched capture and replicates it a **whole** number of times, to a pitch of 32, which is what the reader is told to use. The four real challenge captures on this machine read 3 of 4 correctly at 30.64 and 4 of 4 at 32, and a live boot on 2026-09-08 answered a fresh one and left the party adventuring. Measured on 55 captures of the running game: 5 challenge screens answered, 50 other screens refused, no false positive. |
| `amigacontainercheck.py` | Checks that the Amiga saved game `goldbox.amiga_savegame.new_por_savegame` builds carries the **source save's** own square, facing, clock, area and resident map rather than the one SSI shipped -- the independent evidence behind `#316 (Write the Amiga Pool of Radiance saved game from the source save, so a converted party arrives where it was standing)`. For every C64 save it is given it prints where the source says the party is, where the built container says it is, which of those fields differ from disk 1's shipped `savgamA.dat`, and how many of the 13,141 bytes have a source; exit status 0 when every container matches its own source, 1 when one does not, 2 when there was nothing to check. **Its two ends share no reader, and that is the whole reason the result means anything**: the C64 payload is read by hand at `address - $4900` and the built container at fixed offsets, big-endian, rather than through `goldbox.amiga_savegame.por_word` or `goldbox.world_state`, so a container that agreed with the writer and not with the save would show up. `tests/test_amigacontainercheck.py` asserts neither reader names a library accessor, so tidying one into a call to the code under test turns a test red instead of turning this into a transcript. The three fields the writer *declines* to write are reported as declared rather than as mismatches, with the reason it gives -- outdoors it writes `$49C5` = 0, since a travel window loads a `SQRDATA` rather than a `GEO`, and leaves the indoor square stale. Eight C64 specimens on this machine, 8 of 8 matching. The C64 saves come from `$WISH_SPECIMENS`, the Amiga disks from `tools/registry/gamedisks.py`'s `amiga` entry unless `--data-disk` and `--game-disk` name images; everything is opened read-only and the only file written is `--out`. |
| `amigacursewheel.py` | Answers Amiga *Curse*'s code-wheel prompt so the title can be driven unattended, and records nothing about it. The arithmetic behind the wheel is copy-protection research and `CLAUDE.md` keeps it in Donald's separate private repository, so this reaches into that repository at run time -- `$WISH_CODEWHEEL`, or the `codewheel` entry in `gamedisks.yaml`, the name and default `tools/curse_of_the_azure_bonds/cursewheel.py` settled for the DOS side -- reads the challenge off the guest's screen with its reader, presses the character and RETURN through `amigadrive.py`, and deletes the screenshot. What it prints is `answered` or `no challenge on screen` and never the challenge or the character. One thing it has to do itself: that reader fits the game's font at 3.6 to 4.0 captured pixels per Amiga pixel and `winvm shot` of WinUAE's 720-wide window gives exactly 2.0, so the capture is scaled up by a whole number with nearest neighbour, which invents no pixel. A no-op on the other titles -- Amiga Pool of Radiance's wheel screen takes a bare RETURN and Amiga Silver Blades asks for a journal word instead, which nothing here can answer (`#331 (Amiga Silver Blades asks a journal word before it will adventure, so the title cannot be driven past its party menu)`). |
| `amigadrive.py` | Types at an Amiga game running under WinUAE in the Windows VM, from Linux, and grabs the guest's screen. `winuae.ps1 key` presses one virtual key per call and every call is an ssh round trip through a scheduled task, so what this saves is the name-to-VK table and the waiting: `keys RET L S A V E SLASH RET` is the whole route into Pool of Radiance's `LOAD WHICH GAME:` picker. It takes no lane claim and releases none -- the claim `winuae.ps1` enforces has to outlive any one of these calls, so it is the caller's, and every call is refused without `--holder`. `NP0` to `NP9` are the numeric keypad, which is what walks a party in Amiga Curse and Amiga Silver Blades: `NP8` forward, `NP2` about face, `NP4` and `NP6` the two turns, all measured on the status line (`#361 (An Amiga party cannot be made to walk, because the WinUAE driver sends only keystrokes)`). `UP`, `DOWN`, `LEFT` and `RIGHT` go in with `KEYEVENTF_EXTENDEDKEY`, because without it `keybd_event` hands `VK_UP` the unprefixed scancode `0x48` -- which is `DIK_NUMPAD8`, so an unextended `UP` is keypad 8 under another name and the driver had no way to press a cursor key at all. Nothing it does opens a window on the host. |
| `amigaenum.py` | Names an Amiga Gold Box enumeration from the routine that draws it: finds the sites where a record byte is scaled and used to index a `char *` table, prints the strings a table holds, and lists a `GLIB` text library's blocks. It is what settled that the later Amiga titles number the nine character states DOS's way. |
| `amigaglobal.py` | Finds every instruction that touches a SAS/Lattice small-data global, and every caller of a routine, in Amiga *Curse* and *Silver Blades*. `amiga68k.py refs` searches for PC-relative references, which on those two executables is the wrong search: a variable is `d16(a4)` and a far call is `jsr d16(a4)` through a table of `jmp abs.l` entries, so neither has a PC-relative reference anywhere and `refs` answers "no PC-relative reference" for both. It scans for the displacement word first and decodes a short window around each hit, which cannot desync the way a linear disassembly of a 300KB code hunk does -- taken that way the five Silver Blades square globals came back with 0 references between them where there are 191. It found the step routine from the party's x byte, and that routine's one caller from its jump-table slot, for `#28 (Decode an Amiga saved game, not just a character file)`. Needs `capstone`. |
| `amigalaterproof.py` | Puts a party `goldbox.amiga_later.write_later` converted in front of the running Amiga *Curse* or *Silver Blades*, and reads the engine's answer back off the disk -- the run `#384 (Write an Amiga Curse or Silver Blades character, so a C64 or DOS party has an Amiga to arrive on)` was waiting on, written up in `docs/203-a-converted-later-amiga-party-in-the-running-game.md`. `build` is `amigalaterwrite.py --into` plus the one thing that makes the run a test: **`--first <name>` moves a character to the front of the party**. The writer's riskiest choice is a boolean chain head where `write_por` writes NULL, and a wrong head does not spoil one character -- the loader reads the whole party off one file descriptor, so the stream is left mid-block and everybody *after* the bad one is read out of the wrong bytes. Both C64 saves this converts from keep their only item-carrying character last, where nothing is behind him to be corrupted. `diff` compares our saved game with the engine's own resave block by block, masked by the lists the writers **declare** (`goldbox.amiga_later`'s four and `goldbox.dos_codec`'s six, mapped through the title's shift map) and never by whatever happened to differ, and names each difference by its field or its node offset; it exits non-zero when anything falls outside them. One of `goldbox.amiga_later`'s four, `LATER_WRITE_DERIVED`, is Curse's `thac0_current` and one `roster_tail` byte, which the engine itself recomputes on load (`#402 (Amiga Curse recomputes thac0_current and a roster_tail byte on load, and no declared list says so)`). `porslotdiff.py` is the Pool of Radiance equivalent and does not fit these two, whose party lives inside the saved game rather than in `CHRDAT` files beside it. Every input is opened read-only and `--out` is required. |
| `amigalaterslot.py` | Puts a saved game our own code wrote in front of Amiga *Curse* or *Silver Blades*: reads a slot off a disk image, rebuilds the container through `goldbox.amiga_savegame` with one visible edit, and writes it to another slot on an output image. `porslot.py` is the Pool of Radiance equivalent and does not fit these two, whose party lives **inside** the saved game rather than in `CHRDAT` files beside it. The three edits are each one thing a screenshot can settle -- `--rename n=NAME` for the cheapest proof the engine read our bytes, `--keep n` to move the count word and every later block boundary, and `--strip-items n` to make the loader's test on the chain head decide. It built the five slots `docs/165-amiga-savegame.md`'s "What the running game did with one" was measured on. The input image is opened read-only and `--out` is required. |
| `amigalaterwrite.py` | Converts a C64 or DOS party into Amiga *Curse* or *Silver Blades* records through `goldbox.amiga_later.write_later`, and is the harness for the run that would close `#384 (Write an Amiga Curse or Silver Blades character, so a C64 or DOS party has an Amiga to arrive on)`. Prints one line a character -- the block length the loader will compute, the item and effect counts, the chain heads it tests -- and then, on request, the whole provenance summary, a field-by-field comparison against the Amiga's own record of the same person (`--compare`, which is how the six shipped Silver Blades twins were marked: 150 field comparisons, 0 differing), or a copy of an Amiga disk with the converted party rebuilt into a save slot (`--into ... --out`). The source and `--into` are opened read-only. |
| `amiganodefields.py` | Says which bytes of an Amiga *Curse* or *Silver Blades* **heap node** the game's own code touches, which is how `#387 (The Amiga Silver Blades effect node keeps a byte DOS has not got, and a converted character loses it)` was settled: nothing in either executable reaches offset 1 of an effect node. `amigarecordrefs.py` asks the same question of a character record by searching for the displacement word, and that search cannot work on a ten-byte node -- its fields are `$1` to `$6`, and `$1(aN)` matches 81 instructions in `/Secret` of which none is a node. So `pool` lists every instruction naming the node pool's descriptor, which is every place a node pointer can be born, and says for each whether it allocates or frees and how many bytes it asks for; and `fields` walks forward from every load of the record's chain-head field, tracks which address registers hold a node, runs to a fixed point and prints every displacement read or written through one, with its width. The walk over-approximates on purpose -- it ignores control flow and keeps a register marked until something overwrites it -- so a displacement it does **not** report is one no instruction downstream of a chain-head load can reach, and one it does report has to be read. Both disk images are opened read-only. Needs `capstone`. |
| `amigaportraitmenu.py` | Re-derives `goldbox/portraits.py`'s `AMIGA_POOL_OF_RADIANCE_MENU` -- the Amiga's own fourteen head and twelve body art ids -- off the player's Amiga disks, finding the table by the shape of its run and checking every id against the art in `head.dax` and `body.dax` beside it, so nothing rests on a file offset. `--check` exits 1 if the disks disagree with the stored block, `--art` is the census showing that the Amiga's eighth body is a **different picture** rather than the same one renumbered (its `body.dax` holds `0D`, `18` and `22` as one repeated block, 19 distinct bodies of 21 ids against DOS's 20), and `--montage` draws both ports' twelve menu bodies in menu order for `#194 (Import and export a Pools of Darkness save between DOS and the Amiga)`. `--palette` prints the thirty-two `0RGB` words the boot code copies into the open screen's colour table, found by the shape of the fetch -- three `DATA` hunks here open with a run of small words and only one is read a word at a time -- and the montage is drawn through its first sixteen entries, so it is now evidence about colour as well as shape. |
| `amigaportraitresolve.py` | Settles whether the Amiga Pool of Radiance record's portrait bytes at `0x0BD`/`0x0BE` hold a **creation-menu position** or an index into `body.dax`, which `#480 (An Amiga character whose body is the menu's eighth arrives on the C64 or DOS wearing a different body, because the Amiga reader uses the C64 and DOS menu)` asked and no corpus could answer -- generation produces menu positions under either reading. It finds the menu's two tables in `/program` by the shape of the run the way `amigaportraitmenu.py` does, then asks the executable's own `RELOC32` entries who references them: all four references point one byte *in front of* a table, which is one-based indexing, and each is followed by `adda.l dn, a0` and `move.b (a0), dn` with the record's own byte in `dn`. So the byte is a position, the table's output is the art id, and the answer is CONFIRMED off the engine rather than argued from a range. `--check` exits 1 if the executable no longer has that shape; `--out-of-range N` prints what a value past the end of a table would fetch, because the resolving routine tests each byte for zero and applies no other check -- 24 fetches body art `0x03` and 33 fetches `0x18` off an unrelated table, neither of which anything may rely on. Reads the player's own `.adf` images, loose or zipped, and writes nothing. `docs/188-the-sheet-portrait-per-title.md` is the write-up. |
| `amigarecordrefs.py` | Finds every instruction in an Amiga executable that reaches a **character record** byte -- `move.b $145(a0), d0` and its kin. `amigaglobal.py` answers the same question for a small-data global, `d16(a4)`, and a record is not one: the engine holds a pointer to the selected character and a field is `d16(An)` off it, so a displacement search is what asks "who reads this field". It is how the Amiga ICON menu's wraps, both shipped inter-title importers and `icon_dimension`'s combat test were found for `#396 (Whether an Amiga Curse or Silver Blades record's combat-icon fields share DOS's own numbering is unmeasured)`. Candidates are found by the displacement word and each is decoded from its own start, which cannot desync the way a linear disassembly of a 300KB code hunk does; a two-byte displacement also matches by luck, so the instruction is printed and **a hit is a candidate until the listing is read**. Searches the CODE hunk only. Needs `capstone`. |
| `amigarecords.py` | Pulls the twenty-one Amiga *Curse* and *Silver Blades* character specimens out of the disk images they live in, read-only -- eleven `SAVE/*.guy` pregens on Curse disk 1 and the two saved games whose parties are found by record signature rather than by a table nobody has decoded. `amigasaves.py` does the same for Pool of Radiance and does not find these: it wants files of exactly 288 bytes in a lowercase `save/` drawer, and none of these is either. `tests/test_amiga.py` calls `extract()` when the environment names no directory, so the saves are never only in scratch, which is where the Pool of Radiance specimens were lost from once (`#55 (Decode the Amiga Curse and Silver Blades records)`). |

| `amigashots.py` | Presses keys at an Amiga game under WinUAE one at a time and photographs each one, cropped to the emulator's own screen.
