# tools

Developer scripts, not shipped — the emulator harness, the instance pool, the
disassembly and dump helpers, the code generators. Anything here may talk to a
live emulator, an X server or the player's own disks, which is exactly why none
of it is in `goldbox/`, `editor/` or `wish/`.

**The 95 Python files under `work/` were swept on 2026-09-02** for
`#181 (Ninety-five Python files sit under work/, and some of them are tools
nobody can find)`, asking of each whether somebody would otherwise write it
again. Nine said yes, and they became the six tools `combatshot.py`,
`d6502check.py`, `m68discheck.py`, `overlay.py`, `rostercard.py` and
`whatis.py` below -- six rather than nine because several files in one
directory were one tool between them. Seven of the nine were moved and the
originals deleted; two were copied instead, because a dozen sibling scripts
import them and deleting them would break the record of the runs that used
them.

The other 86 are a run's output: an emulator driver edited into its own
successor, a measurement of one window, a copy of a package file taken before
a change. They stayed where they are, and moving them would have cost this
table, which is the only thing that makes a tool here findable. A later sweep
starts from what has been added to `work/` since that date.

| file | purpose |
|---|---|
| `__init__.py` | Empty. |
| `amigadrive.py` | Types at an Amiga game running under WinUAE in the Windows VM, from Linux, and grabs the guest's screen. `winuae.ps1 key` presses one virtual key per call and every call is an ssh round trip through a scheduled task, so what this saves is the name-to-VK table and the waiting: `keys RET L S A V E SLASH RET` is the whole route into Pool of Radiance's `LOAD WHICH GAME:` picker. It takes no lane claim and releases none -- the claim `winuae.ps1` enforces has to outlive any one of these calls, so it is the caller's, and every call is refused without `--holder`. Nothing it does opens a window on the host. |
| `coldread.py` | Reads one title's own tables off its own disks, with no emulator: where `GEN` seeds a character's racial traits from, what it caps a class at, which races it limits, and which overlays touch the save's four active-effect arrays. Every table is **found by the instruction that reads it** rather than named by an address, so the same four questions can be asked of Champions of Krynn, Death Knights of Krynn or Gateway to the Savage Frontier and will either answer or say plainly that they did not -- which is what made `#31 (Cold-read Curse and Silver Blades for the fields the editor shows)` a reading rather than six separate disassemblies. It knows `GEN` and `CAMP` run at `$0800` and that their PRG headers claim four different other addresses; `--base` is there for a title where that stops holding. |
| `combatshot.py` | Draws the automapper's combat canvas and prints what it was drawn from -- all four effect arrays raw, the effects running, who the reader calls helpless, every combatant, and **every combatant's tooltip**, which a `grab()` does not paint. Reads a running machine, or builds `tests/gamedata`'s arena with `--synthetic` so the drawing half can be looked at with nothing booted; `--helpless` marks a combatant in that made-up memory, which is the only way to see the badge, since no save this project holds carries one. Exists because the two halves mislead separately: a canvas that draws nothing and a machine with no fight running make the same PNG. Rescued from the helpless-badge run under `work/`. |
| `compare.py` | Loads every character specimen we have and reports, per record offset, how much the value varies — offsets that vary are candidate fields, and correlating that variation with attributes we already know is how the rest get identified. No emulator needed. |
| `d6502.py` | A small 6502 disassembler: given a raw overlay image, a load address, a start address and an instruction count, prints the addresses, bytes and mnemonics. Rescued from `work/rolls/` during the 2026-09-01 tidy rather than lost with the rest of that scratch — the research it supported (`docs/147-combat-rolls.md`) used it to turn `COMBAT` and `LIBRARY` into readable listings. |
| `d6502check.py` | Checks `d6502.py` against capstone, once over every byte value and once over whole overlays end to end -- the answer that has to be got again every time that hand-typed table is touched, since a wrong mnemonic in a listing is what gets believed and written into a document. It catches a real fault: the copy of the table in `work/d6502/before.py` has `SBC` where `$F6` is `INC`, and the table sweep names it. `BRK` is excepted by declaration, `docs/148-d6502.md`. capstone is a cross-check and not a dependency of `wish`, which is why this is a tool and not a test. Rescued from `work/d6502-plan/`. |
| `diff.py` | Diffs two save disks and says what changed in game terms. The workhorse of the discovery phase: save, change exactly one thing in-game, save again, diff. Changed bytes resolve to slot plus record offset and are labelled with the layout field or flagged as an unknown region — the unknown hits are the interesting ones. |
| `dosbox.py` | A driven DOS Gold Box session: DOSBox on a private X display, unattended. Input is XTEST through `xdotool` aimed at a window nobody else owns (there is no window manager under a bare `Xvfb`, so `windowactivate` fails and the keystroke is lost); output is a 320x200 capture that is the VGA framebuffer pixel for pixel; ground truth is the save file DOS writes. The window is chosen by `_NET_WM_PID` and then proved to have pixels in it, a display something already answers on is refused rather than shared, and a screenshot of one flat colour is refused by name (#88). |
| `dosboxx.py` | The DOS debugger harness: `dosbox.py`'s session with the launch replaced by a DOSBox-X built `--enable-debug=heavy`, on a pty so its ncurses debugger has a terminal. Memory reads, `BPM` watchpoints, code breakpoints, registers, single-stepping and writes, over a log file — the DOS answer to VICE's binary monitor. Hides the four traps that cost an hour each: the 64K `MEMDUMPBIN` wrap, the spurious first `BPM` hit, the code breakpoint that logs nothing, and the 254-character command truncation. Displays :40-:47. |
| `dosdisk.py` | Builds a C64 save disk from a DOS save folder, owing nothing to another save -- the command-line form of what `File > Import` does after #118. `goldbox.dos.new_save` writes all 9216 bytes of `SAVEDGAME0` and `SAVEDGAME1` from two zeroed buffers and `save_disk` puts them on a `D64.blank()`; the two things no DOS save can supply, the composed combat icon and `ANIMATE00`, are read off the player's own `POOL` sides at run time and the tool refuses without them. `--sheet` prints the DOS party the way the C64's `VIEW` screen lays it out -- name, race, alignment, class, the six abilities, level, experience, hit points, armour class, THAC0 and money, with `armour_class` and `thac0_current` decoded through the family's `60 - value` -- which is the side of the #119 comparison a person reads against the running game. |
| `dossavgam.py` | Surveys every DOS Gold Box saved-game container on the machine and prints what each one is made of — the title's shape and region map, the party table, the party size, and the two variables that agree with the header byte. `--runs` prints every run of nonzero bytes before the party table, which is how the per-title region map in `goldbox/dos_savegame.py` was read off in the first place, and `--scripts` gives the largest `ECL<n>.DAX` block per title against the 7680-byte staging buffer. Deduplicates on the bytes, because the archives ship most save directories twice. Reads only, and reads the player's own archives; nothing it prints is committed. |
| `dosfightrun.py` | Drives a DOS Pool of Radiance fight to its end, and the capture run that made that possible. `capture` presses a ladder of keys at whatever is on the screen and logs every quarter second -- bar, status and whole-frame digests, a PNG the first time each command bar appears, and the save files either side -- which is how the digests in `PoolOfRadiance.COMBAT_BARS` were read and how `QUICK` was put to the test. `fight` is the driver those digests made possible. Ground truth is the save file: experience rising in `CHRDAT<slot><n>.SAV` says monsters were slain and so names the party as the killer, where hit points falling says only that the party was struck. The runs' output goes to `work/dosbox/p114/`; the tool does not. |
| `dosnewsave.py` | Builds a DOS *Pool of Radiance* saved game from a C64 save disk with no template, boots it under DOSBox and reads the party off the game's own screens -- the acceptance check behind #26, and the DOS-side twin of `dosdisk.py` and `savecheck.py`. `goldbox.dos.new_dos_save` writes all 13137 bytes of `SAVGAM<slot>.DAT` and every `CHRDAT<slot><n>` beside it from 13137 zeroes, and the run is what turns the file's declared zeroes into measurements: the party loads, its sheet and item list are captured, `--steps` walks it (turning when a step is refused, fighting when something interrupts), and the game's own `ENCAMP > SAVE` writes the slot back so the resave can be diffed against what we wrote -- the engine's own rewrite being the oracle for which zeroed bytes it fills in for itself. The game tree is staged into the instance's work directory first, so the archives stay read-only. |
| `dosoutdoor.py` | Makes an engine-written DOS *Pool of Radiance* saved game on the overland travel grid, which nobody's own save is: all three of Donald's are indoors, and the three made for #50 and #59 in 2026-08 lived in `work/` and are gone with the script that made them. Reaching the grid by playing means crossing New Phlan to the harbour master and taking a boat, so it seeds and resaves instead -- `dos_savegame.retarget` moves a *copy* of an indoor save onto a travel window, and on top of it the four fields measured to differ outdoors: `$49C5` = 0, `$49E6` = 0, the travel square at `$49C3`/`$49C4`, and the outdoor tail state. DOSBox loads that seed, `--steps` walks the party, and the game's own `ENCAMP > SAVE` writes the specimen -- so every byte of it is the engine's, and the seed is kept beside it named as a seed so a reader can tell which is evidence. The player's game tree is copied before anything is written. |
| `drive.py` | Drives Pool of Radiance under VICE — the original binary-monitor client (still re-exported from `automap/vice.py`), key sending through XTEST on the nested display, and the surrounding discovery scaffolding. |

| `eclflags.py` | Every reference the thirty area scripts make to the quest-flag page `$4A00`-`$4AF8`, classified into reads and writes and keyed by address -- the regenerable replacement for `work/reports/quest-flags.md`, which was lost with `work/reports/` (#136). It walks the scripts with `eclwalk.py` and knows from the instruction set which operand of each opcode is a destination, so `SAVE 250, [$4A04]` counts as a write and `COMPARE [$4A04], 250` does not; `sites 4A81` prints every instruction that touches one address, which is how a new quest gets read. `doc` regenerates `docs/151-quest-flags.md` whole. It prints no string as text -- the English in its last column is joined out of `goldbox/commissions.py`, so the table cannot drift from the code and none of the game's own words reach the repository. |
| `eclwalk.py` | Reads an area script statement by statement and prints, per exit, exactly what a fast travel skips. Every number it needs comes out of `DUNGEON` at run time -- the opcode handler tables, the operand count, and the three shapes `$1663` decodes -- so it cannot drift from the game. It walks each script from its five entry addresses following `GOTO`, `GOSUB`, `ONGOTO`, `ONGOSUB` and both arms of every `IF` rather than sweeping it linearly, because a linear sweep runs into the data tables opcode `$2A` indexes and turns them into nonsense; it reaches 98% of all 178035 bytes of the thirty scripts. Rebuilt for `docs/150-departing-prologues.md` after `work/analysis6/ecl6.py`, which decoded all thirty to 100% of every byte, went with `work/` (#136). Prints a string operand as its length and never as text, because its output goes into a repository the game's words must not enter. |

| `m68dis.py` | A 68000 disassembler that **refuses to guess**: a word it does not recognise prints as `dc.w $xxxx`, never as the nearest instruction that fits, because a made-up instruction in the middle of a string table is what gets believed and written into a document. Every field is checked before a mnemonic is emitted — an addressing mode the opcode cannot take, a 68020 index extension, a branch to an odd address. The last two are legal encodings on real silicon; refusing them is a judgement that **no assembler emits them**, so a word carrying one is data. Branches, `dbcc` and PC-relative operands print the address they reach, so a target needs no arithmetic. `--refs ADDR` walks a range a word at a time and reports every instruction pointing at one address, which is how the code that opens a `.pc` was found from the string alone. Reads a plain binary at file offsets; it does not parse AmigaDOS hunks, so give it `--offset`/`--length` inside the code hunk, and nothing outside that window is read — an instruction that would cross the end of it prints as `dc.w` rather than disassembling the next hunk. Verified against capstone 5.0.7 in `CS_MODE_BIG_ENDIAN | CS_MODE_M68K_000` over 100 385 instructions of the Amiga *Pools of Darkness* binary: no length disagreements, no operand disagreements, nothing capstone decoded that it refused — `docs/50-experiments.md` §"The 68000 disassembler". |
| `m68discheck.py` | Checks `m68dis.py` against capstone over a real Amiga binary, in both 68000 and 68020 mode, and accounts by name for every word `m68dis` refused -- an odd branch target, a 68020 index format, a 68020-only instruction. That is the run behind the claim in `m68dis.py`'s own row: 100 385 instructions, no length disagreements, no operand disagreements, nothing capstone decoded that it refused. Running both modes is the point rather than thoroughness: in 020 mode capstone decodes instructions the target CPU does not have, so a comparison that does not say which mode it used says very little. The binary is not in this repository and is a required argument. Rescued from `work/issue-148/`, whose own comment said it belonged under `work/` -- which is how a check nobody can find goes unrun. |
| `instance.py` | The VICE instance pool: six resources per slot (two monitor ports, a command port, an X display, a work directory and a private `vicerc`), held by one lease. | `livelevel.py` | Raises a character's level on a **running** machine, by replaying through `automap.actions.LevelUp` what the training hall writes (`docs/135-levelling.md`). It writes experience before every level because the trainer clamps it, which leaves a character one point short of the next threshold otherwise. | `outdoorwalk.py` | Walks a party on the C64 travel grid and reads the square out of memory, which is the only way to see an outdoor step. `tools/savecheck.py` cannot: outdoors the status line reads `OUTDOORS 22:02 7,28` with the word where the facing letter goes, so `session.py`'s `walk_one` has no facing to turn from, re-sends an invisible turn until the party has come full circle, and falls back to `$49C0`-`$49C2`, which out there is the frozen square the party left the grid on. This reads `$49C3`/`$49C4` through the binary monitor before and after every key and polls rather than sleeping, since an overland step is hours of game time. **The overland move bar is `1-8, RETURN OR BUTTON`**, not the dungeon's `I J K M`, so `--moves` takes compass digits; a run driven with `I` moves nothing and looks exactly like a save that cannot walk. It is what proved #50's converted overland party takes a step. |
| `overlay.py` | Reads a named game overlay at the addresses it **runs** at -- `hex` dumps a range, `refs` finds every mention of one address with the byte in front of it, `dis` disassembles. | `winuae.ps1` | Starts, stops, raises and drives WinUAE on the Windows guest through `winvm ssh`. Every action goes through a scheduled task with an Interactive principal, because `winvm ssh` lands in session 0 and the VM's screen is session 1: a GUI process started from session 0 is invisible to `winvm shot` and cannot be focused from there. `key 7A` presses F11 into the emulator, which is what opens the debugger, and `roms` points WinUAE's ROM database at `C:\Amiga\Kickstarts` and rescans it without a GUI, so a person who opens the emulator is not told there are no Kickstarts. Every action reports `ok` or `fail` and exits accordingly: an Interactive task started with nobody logged on at the console runs nothing and says nothing, and a task started while its own last instance is still alive is ignored outright and hands the caller that instance's receipt — which is how a whole run can report success and produce empty dumps. So each call stops the task before starting it and matches a token of its own in the receipt, `start` refuses to run a second emulator over the first, and `clean` refuses while one is running, since unregistering the task would strand it where the only way out is a kill by name. Two emulators are refused rather than guessed between: `roms` launches its own for the scan, so it refuses over a live one, and `front`, `key` and `send` refuse when they find more than one and name both pids. The VM is single-tenant and now says so: `claim -Holder <id>` refuses a second holder, `start`, `stop`, `key`, `send`, `front` and `roms` refuse a caller who is not the holder, `start` checks that the emulator it found is running the command line this call passed and writes a receipt naming the pid, and `stop` refuses a `winuae64` that receipt does not describe — because with one task and one process name a second agent does not get a second emulator, it gets yours, and before this its `stop` ended somebody else's session three times in one night. `tools/winuae-lanecheck.ps1` is the proof. The claim is an atomic file create plus a read-back of the caller's own token, not a read-then-write: six claims arriving together used to grant the lane to all six. Every refusal carries the `-Override` line that clears it, because a lane whose holder has died is otherwise a lock nothing tells you how to open. A holder re-asserting a lane it already holds writes nothing at all, because deleting the file first left it reading free for long enough that somebody else could take it without asking. `send` reads `send.log` through a handle that shares the file with the injector appending to it, because the plain `Get-Content` poll was what collided with the injector's `Add-Content` and killed it. |
