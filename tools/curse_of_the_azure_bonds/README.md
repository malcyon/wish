# curse_of_the_azure_bonds

Scripts for Curse of the Azure Bonds: loading, driving and checking its saves.

| file | purpose |
|---|---|
| `curseareazero.py` | What a *Curse of the Azure Bonds* save holds before the party begins adventuring, for `#301 (A DOS Curse save standing in area 0 is refused by the import, because no row of the area table names area 0)`. Boots C64 Curse to the party-formation menu and reads `$4B00`-`$4DDF`, which is what `SAVE CURRENT GAME` would write there: area 0, map 0, disk hint 2, twenty-five zero cache slots, clock 00:00, the same numbers a DOS save made at the same menu holds. `--save`/`--begin` then load a disk and press `BEGIN ADVENTURING`, stopping on the status line, and read the KERNAL's `SETNAM` state when the game asks for a disk -- which is how the file an area-0 save sends the loader after was named as `GEO00`. `--doctor SRC DST` is offline and stamps the never-adventured header into a copy of a save disk; `--zero` takes the four fields away one at a time, because a run that changes four bytes at once and crashes has proved nothing about any of them, and `--recipe` builds the cache `goldbox.dos_codec.apply_file_cache` would write. `--patch-early` moves `curserun.DISK_PROMPT_PATCHES` back to the party menu, which was suspected of killing the machine and cleared: the same disk crashed with no patch at all. |
| `cursecheck.py` | Boots a *Curse of the Azure Bonds* save disk in VICE and reads the party off the game's own screens -- the Curse twin of `tools/c64/savecheck.py`, and the thing `#52 (File ▸ Import and File ▸ Export for every direction the library supports)`'s fifth flag condition was missing. `curseload.py` gets a party in through the game's own `LOAD SAVED GAME` and then serves, so that condition's DOS → C64 Curse row stood at PROBABLE with nobody having read a panel, a sheet or a step off one. This reads the status line, the roster panel under its own `AC` heading (`#104 (A converted DOS party arrives with the template save's spare characters still in it)` -- how many rows it lists is the party size), every character's `VIEW` sheet by walking the panel highlight, and a walk one key at a time. It records **both** the status line and the live triple at `$C04B` on every step, because Curse does not print the square in every area -- area `$03` draws `E 3:44` and no coordinates at all -- so a status-line reader alone proves nothing outside the areas that do. `--resave` has the engine's own `ENCAMP ▸ SAVE` write the party back and copies that disk out, which is how an engine-written save of a converted Curse party is made. Two things it needs come from `curserun.py` rather than from here: Curse's move handler answers only the KERNAL buffer, and Curse has no travel grid, so `Session.indoors()` must not read Pool of Radiance's `$49E6` (`#360 (The session driver will not walk a Curse or Silver Blades party in a dungeon, because it reads Pool of Radiance's indoors flag)`). Output goes to `--out`, under the temp directory; the player's disks are read only. |
| `cursedisk.py` | Builds a *Curse of the Azure Bonds* C64 save disk from a DOS save folder, which `tools/dos/dosdisk.py` cannot: that one writes Pool of Radiance's `SAVEDGAME0`/`SAVEDGAME1` pair and never names a `Game`, and Curse's container is one 7424-byte `SAVEAZURE` at `$4B00` with eight slots, a name table, eight item pages, `ANIMATE00`'s picture buffer and the roster all inside the one payload. `goldbox.dos_codec.new_save(game=CURSE_OF_THE_AZURE_BONDS)` writes every byte of it and refuses a payload with an unsourced byte in it; the combat icon and `ANIMATE00` come off the player's own Curse sides at run time, so the tool refuses without them. It reaches past two things the shipped code still does, in its own process only and never on disk: `goldbox.dos_codec.CONVERTS` holds Pool of Radiance alone, and `goldbox/areas.py` has no Curse rows -- the twenty-five `#192 (Convert a Curse of the Azure Bonds DOS save into a C64 one, which the importer refuses today)` step 0b measured are carried here, and `--check-areas` re-derives them off the disks through `tools/areas/areatable.py` and diffs them rather than trusting the copy (25 of 25 agreed on 2026-09-05). `--sheet` prints the DOS party the way the C64's `VIEW` screen lays it out, which is the side of the comparison a person reads against the running game, with the memorised-spell count added because Curse gives that list 69 slots. |
| `curseflee.py` | Drives a Curse of the Azure Bonds party into a fight and tries to flee it, for #445 (The game's third fight outcome, THE PARTY RUNS AWAY, has never been seen on a screen): `curserun.CurseSession` and `curseload.py` boot and load, `tools/pool_of_radiance/fleedrive.py`'s `Flight` tactic does the fleeing. Needs `--save` (a Curse save disk) and a pool slot; logs, a screenshot and the final screen go under `--out`. |
| `curseload.py` | Gets a party into *Curse of the Azure Bonds* through the game's own `LOAD SAVED GAME`, and measures it when it refuses. `GEN $1F42`'s loader is `LIBRARY $3159`, a plain KERNAL `LOAD` whose name pointer is written into the operands of `$319F`; `$401E` turns the result into a number, and with no fastloader installed (`$7E9F` = 0, which is the party menu's state) that number is the **1541's own error code** at `$03F1` -- 62 the save disk was never in the drive, 74 the load was taken inside the drive's settling time after the attach, 60 the image's `SAVEAZURE` is a file the drive never closed. `load_saved_game()` is the sequence any other Curse tool should call; `--repair` closes a splat entry in the staged copy, `--count` counts `GEN $1F30`, `$183A`, `$1F48` and `$1F4D` so a prompt too brief to photograph can still be proved drawn, and `--pre-fail`, `--attach` and `--prompt` are the differentials that separated the three faults (`docs/179-loading-a-curse-save.md`). |
| [cursepaladin.py](cursepaladin.py) | Dual-classes a C64 *Curse of the Azure Bonds* paladin or ranger through the party menu's own `HUMAN CHANGE CLASSES`, trains him past the level he left his old class at, and keeps the record `GEN $20A3` writes -- the run that made `WISH-SPEC-curse-409-regained-paladin`, the first C64 record anywhere whose `class_bits` is a pair `GEN $1951` has no class code for (`#409 (A regained dual-classed paladin or ranger has a class mask Curse's own table cannot name, so Wish shows him a class he is not)`). `stage` writes ability, level and money **inputs** into named slots and says which, putting an ability into both of the record's two arrays because `GEN $1E9C` copies one into the other; `run` boots on a pooled slot, loads through the game's own front end, drives the change, stages the new class's level array entry to `dual_class_level` so **one** training press crosses the regain test rather than six, photographs every screen it presses a key on, and photographs the `VIEW` sheet -- which is where the game's own answer is, `CLERIC/PALADIN` and `LEVEL 6/5`. Three things cost a run each and are carried here: `VIEW CHARACTER` puts up a picker and not a sheet, a training leaves the `TRAIN WHO` list up so the next menu lookup spends its whole timeout, and `SAVE CURRENT GAME` asks `SAVE GAME ? YES NO`, which like Curse's other bars answers only the KERNAL buffer. `show` prints a save disk's class fields with no emulator. |
| `cursepic.py` | Decodes a Curse `PIC` file's animation frames with `ANIMATE00`'s own XOR-run unpacker (`$6AC0`), and says which frame a `SAVEAZURE`'s `+$1800`-`+$1BFF` holds -- that region is the picture buffer at `$6300`, not map memory (`#283 (What Curse keeps in the area map region at +$1800 is unread, and a conversion writes zeroes there)`). `frames PIC1D --png DIR` renders each frame; `match SAVE.D64` exits 0 only on a byte-for-byte frame |
| `cursepicrun.py` | Drives a Curse session to watch the picture buffer: loads a save, overwrites `$6300`-`$66FF` with `$A5`, counts loads and stores of it through the world and a walk, catches the first store on `ENCAMP` with its PC and the load count at that instant, then samples the buffer to watch `PIC1D`'s frames cycle (`#283 (What Curse keeps in the area map region at +$1800 is unread, and a conversion writes zeroes there)`) |
| [curseregain.py](curseregain.py) | Trains a DOS Curse dual-classed human past the level he left his old class at, under DOSBox, and keeps the record the engine writes -- the run that made `WISH-SPEC-curse-408-regained-paladin`, the first DOS record past that threshold anybody here watched being written. Stages a class level, an experience total and the hall's class filter at `SAVGAM+0xD51`, trains one or more roster lines at the party menu, saves with ENCAMP > SAVE, and prints the class fields before and after. `--who 1,6` trains a dual-classed character and a single-classed one of the same class in the same boot, which is what makes one reading a measurement. |
| `curserun.py` | A driven *Curse of the Azure Bonds* session on a pooled VICE instance: stages the six sides and a save disk, boots the release past its title, credits and start-up check, answers Curse's three disk-prompt wordings, and patches the disk-swap prompt that cannot otherwise be answered. That prompt is the harness fault this tool exists around -- the loop at `$453B` leaves only on a key read plus a command-channel answer of `00`, and the drive answers DOS error 62 continuously; three explanations were measured and all three came back negative (`#32 (One Curse session, to get a party with items)`). It produced the first Curse save anybody has that carries items, by shopping in Tilverton rather than fighting. |
| `cursesavediff.py` | Diffs two Curse `SAVEAZURE` payloads and labels each run of differing bytes with the region it lands in and whose byte it is -- `engine` for a region the game rewrites for itself, `ours` for one where a difference is a conversion fault, `?` for one nobody has attributed. The engine's own `ENCAMP > SAVE` is the oracle a conversion is checked against, and 7424 bytes of `cmp -l` is not how anybody tells the game's bookkeeping from our mistakes: on `#192 (Convert a Curse of the Azure Bonds DOS save into a C64 one, which the importer refuses today)`'s run it turned 538 differing bytes in 97 runs into four lines, all four `engine` -- `ANIMATE00`'s picture buffer, a frame of the camp scene (526), the loaded-files cache the arriving script refills (9), the two per-area constants `ECL01` writes at its head (2) and one clock digit. Takes a `.d64` or a raw payload either side, prints payload offsets (add `$4B00` for the running machine's address), and exits non-zero while any run lands in a region a conversion writes, so a run can be a check. |
| `cursethac0.py` | Answers whether a *Curse of the Azure Bonds* fight reads the stored `thac0_current` or works the number out again, which is `#368 (Does the C64 Curse engine read thac0_current in a fight, since the training hall overwrites it with the base and loses the strength bonus?)`. `stage` copies a save disk and puts `0x0A` -- THAC0 50, twenty-six below anything `GEN $1F1F` can produce -- into a named character's roster block, optionally forcing `strength_bonus_flag` at `0x0E3` so two spoiled characters predict two different answers; it closes the splat directory entry every image copied out of a pool slot carries. `run` claims a pooled VICE slot, boots, loads through the game's own `LOAD SAVED GAME`, reads the roster page at `$6700` and the staged record at `$7C00` at every stage, walks to a square on a route planned from the area's own `GEO` passability -- a greedy walk cannot leave Tilverton's start, because the door north of `7,12` is locked -- and presses `PUNCH BARKEEP` for the cheapest fight in the title. Two counting checkpoints on `LIBRARY $3918` and `$394B` say when the rebuild ran, which is what separates "nothing recomputed" from "it recomputed to the same number". `show` prints both regions of a save disk with no emulator. Reads the player's disks only; every image the game sees is the slot's own copy. `docs/205-the-c64-thac0-rebuild.md`. |
| `cursethiefskills.py` | Why a DOS Curse thief's eight stored skills sit seven points above the tables: finds each DOS engine's thief-skill routine in the player's own `GAME.OVR` and reports whether it initialises the stack local it adds to every column, sweeps every Curse record on both ports against that port's tables, and counts which files on the C64 disks draw a thief-skill label |
| `cursetrain.py` | Stages a *Curse of the Azure Bonds* save disk with experience, platinum, constitution, the class bits, the dual-class pair, the rolled hit points and any per-class level written into named character slots, boots it on a pooled VICE instance, and diffs a before/after record pair against `goldbox.levelup.plan`. The lever is `GEN $12AF`, which builds the party menu's item mask and clears bit 3 -- `TRAIN CHARACTER` -- whenever `$7EA8` is zero: the area scripts write 127 there when the party is in a hall (`ECL01`, `ECL03`, `ECL50`, `ECL51` each issue `SAVE 127, =[$7EA8]`) and `GEN $2029` puts it back to 0 on the way out, so poking one byte from the monitor opens the hall wherever the party stands and saves a session of map-reading. `stage` writes only input fields, says which, and `--repair` closes a `SAVEAZURE` the drive never finished so the image loads (`#298 (A save disk copied out of an emulator slot before the drive closes the file cannot be loaded by the game)`); `run` boots and serves rather than pressing keys, because four things in this front end have to be watched (`docs/172-curse-trainer.md`); `diff` prints the field-by-field delta and replays it through our own module, reaching past `levels.TRAINER_MEASURED` in its own process only -- 75 of 75 derived fields across five driven Curse level-ups on 2026-09-05. |
| `cursewarp.py` | Fast-travels a running *Curse of the Azure Bonds* party, which is what answered `#19 (Can Curse be fast-travelled at all, or is the mechanism Pool of Radiance's alone?)`: it stages the six sides and a save disk into a pooled slot, boots, loads the party, makes `NEWECL`'s own five writes from outside and drops the PC into the handler's tail, then reads back the map at `$0400` and drives the party one key at a time to prove it can walk. **Every address is re-derived from Curse's own overlays at run time** through `tools/areas/newecl.py`, so nothing is Pool of Radiance's with an offset applied by hand. It carries three things about driving Curse that `tools/c64/session.py` does not know and that cost most of that session: the load bar reads `LOAD SAVED GAME ? YES NO` rather than Pool of Radiance's `LOAD SAVED GAME: YES`, that `YES` answers only to the KERNAL buffer and not to an XTEST Return, and the game never prompts for the save disk there -- it reads `SAVEAZURE` off whatever is in unit 8 and says `UNABLE TO LOAD SAVED GAME.` It refuses a warp out of the travel grid without `--force`, on Pool of Radiance's precedent that it wedges the loader unrecoverably. |
| `cursewheel.py` | Answers DOS Curse's code wheel off a screenshot, which is what stands between an agent and a driven DOS Curse session, and records neither the challenge nor the answer (`#108 (Amiga Curse asks its code wheel, so the title cannot be driven unattended)`'s ruling). The prompt draws an Espruar rune above a Dethek one as two embossed tiles at (143,31) and (143,63); everything in a tile that is not the two background greens or the border's two greys is the glyph, and that mask is matched against `coab/images/`'s C64-rendered runes as normalised grids with a cell of slack -- a strict overlap ranks the right rune no better than the wrong one. The path is read cell by cell: a dot is a 3x3 diamond, a dash a 7px bar two rows tall, each one to a character cell, and a dash prompt marks only every other cell of its nine -- so what is read for is a run of five or more marked cells with nothing but text between them, not five in a row (`#537 (tools/curse_of_the_azure_bonds/cursewheel.py never recognises a real DOS Curse code-wheel screenshot, so its own command line refuses every prompt)`, which the first `read_path()` never matched against a live capture). The box number is not read and is passed with `--box`. The command line prints only `challenge on screen, answered`, `challenge on screen, not answered` (including when the path could not be read, which used to be folded into the next outcome) or `no challenge on screen` -- never a rune index, a score, the path or the character typed; `answer` and `identify` stay importable for a driver to use in process, the shape `tools/amiga/amigacursewheel.py` follows for the Amiga side of the same wheel. The wheel table and both ports' arithmetic come from `$WISH_CODEWHEEL`, or the `codewheel` entry in `gamedisks.yaml`, which is outside this repository deliberately. |
| `doscurse.py` | A DOS Gold Box session driven a command at a time out of a text file, with a screenshot after every keypress -- the half of the harness `tools/dos/dosbox.py` cannot be, since its digests only recognise screens somebody has already measured. Curse's and Silver Blades' camp menus were walked with it for `#113 (Play DOS Curse far enough to save a party with items)`, which is how the party-panel highlight turned out to move with `Home`/`End` in Curse and the arrow keys in Silver Blades -- eleven candidate keys refuted per title, and the Archives' own `Controls.pdf` says `PgUp`/`PgDn`, which is wrong. |
