# c64

Scripts for the Commodore 64 titles: the VICE session and the drivers built on it, save and record checks, and the C64 Ultimate tools.

| file | purpose |
|---|---|
| `abilitypair.py` | Separates the two ability arrays a later C64 title keeps -- `0x014` and `0x065` -- and says which one the engine uses, which is what settled `#367 (What is the second ability array at 0x065 for, and which of the two does the engine treat as current?)`. Every specimen anywhere holds the two byte for byte identical, so no save can answer it: `stage` writes them **apart** (`--set PHILIPPE:str=9/18`) so a boot can, and `read` prints both arrays for every character beside the bytes the engine derives from them -- the carrying allowance at `0x0E2`, the dexterity index at `0x0EC`, and the strength-drain counter at `0x0FF` that Pool of Radiance spends on a portrait. The `0x0E2` line is the one that discriminates: it reproduces `LIBRARY $19EE` and prints what each array would have predicted, so a record where the two disagree names its own source. `refs` is the static half, a per-file census of both windows. Nothing is written but the copy `stage` makes. `docs/201-the-two-ability-arrays.md` is the write-up. |
| `absrefsweep.py` | Which of a C64 title's files name an address in a window, and where -- the header's answer to what `recordsweep.py` asks of the character record, and the general form of it, since it takes an absolute window rather than a record offset. It is what settled `#192 (Convert a Curse of the Azure Bonds DOS save into a C64 one, which the importer refuses today)`'s step 0e: a census of `$4B00`-`$4EFF` over Curse's 411 files found **zero** references to payload `+$EA`, Pool of Radiance's disk hint, against five in Pool of Radiance -- and `+$EE` instead, read by `GEN $2008` on load and written by `CAMP $0C8D` on save. `--sites` disassembles around each hit. A hit is a claim about bytes and not proof they are code, so art files and `ECL<id>` script bytecode are counted separately from the overlays; without that split the same sweep reports 597 references that are bitmap byte pairs and VM operands. |
| `bamsweep.py` | Reads bytes 144-255 of track 18 sector 0 -- the BAM's disk header -- on every `.d64` it is given, and counts how many agree with the layout in `docs/10-disk-format.md`. Written because the 1541 User's Guide's own header table (September 1982, p. 66) prints two byte ranges that cannot both be right, and the way to settle that is to count disks: over the 79 images on this machine the shifted spaces are bytes 167-170 on 73 and the nulls run from 171 on all 79, and every exception is a cracked or hand-built image whose header was rewritten. It also separates a drive's own work from a build script's, since a formatted disk carries `2A` at 165-166 and nine of those 79 do not. Reads only; takes files, directories, or nothing and falls back to `$POR_DISKS`. |
| `c64addchar.py` | Drives the C64's ADD CHARACTER TO PARTY on a pool slot and counts what reads record `0x0E6`-`0x0E7`, which is how `#258 (The C64 side of 0x0AB is unnamed, so the conversion drops it with no issue behind it)` was checked in the running game after the code said nothing reads the pair. Three load watchpoints that do not stop the machine -- `$6BE4`-`$6BE5` (referenced by nothing), `$6BE6`-`$6BE7` (the pair) and `$6BE8`-`$6BE9` (experience, the positive control) -- through LOAD SAVED GAME, two REMOVEs, the add list, VIEW, SAVE and a walk; a block copy reads all three alike, so a field read shows on one. The staged copy of `PORSAVE.D64` carries BRUTUS's record under MALCYON's name and MALCYON's record under the name TWIN, so one boot also shows what the add screen tests: the name, and nothing else. Every screen is kept as text and PNG beside `addchar.jsonl`; the player's disks are never written. `docs/170-c64-identity-pair.md`. |
| `c64addprobe.py` | What `ADD CHARACTER TO PARTY` matches on, driven in the running game. A parked character on a Curse of the Azure Bonds or Secret of the Silver Blades save disk is a whole 580-byte record in a file named for him, and `docs/216-the-c64-name-table.md` established by reading the overlay that the add list is built from the **directory** rather than from the records. This stages a disk whose file name and stored name disagree -- `\x02ARDXYZ` holding a record that still says `ARDEN` -- and reads what the game offers: `ARDXYZ`, confirmed in VICE on 2026-09-08 for `#439 (A rename in Wish leaves a parked character's own file on the C64 save disk under the old name)`. The question it has **not** answered is whether completing an add deletes the source file, which is what decides whether that ticket's smaller fix is even well defined; `--pick` and `--out` are there to take it further. Boots through `tools/curse_of_the_azure_bonds/curserun.py`, claims a pool slot, writes a screen and a photograph per step, and copies the save disk out at the end. Reads the player's disks, writes only into its own slot. |
| `c64clock.py` | Finds the six-digit game clock in every C64 title's overlays by the shape of its tick loop and its status line, saying which title's save page each writes and what limits each digit rolls at — the measurement that settled `c64_port.SHOWN_CLOCK_OFFSET = 0xC7` against `c64_save.Container.clock = 0xC6` as two fields rather than a contradiction (`#470 (Give the project a neutral title beside its neutral character record, with one port per platform a title shipped on)`) |
| `c64monsterlabelcensus.py` | Reads the name out of every `MON*` file on the three C64 titles' disks and runs it through the first-letter-of-each-word label rule for `#345 (Draw a letter in each combat-map square saying what is standing there, instead of the index the backend counts with)`: per title, the counts, the longest labels, names with a hyphen or apostrophe, and every label two different names share. Disks come from `tools/registry/gamedisks.py` or `--pool`, `--curse` and `--ssb`. Read only. |
| `c64nametable.py` | What the `+$C00` party-name table on Curse and Silver Blades is for, in three modes. `show` puts the stored table, the disk's own `\x02`/`\x05` character files and the party records side by side; `sites` finds the six `$5700` instructions in that title's own `GEN` and names each by the shape of its loop, and reads the filename prefix byte off the `S0:` scratch template rather than off a table; `run` boots a save disk in a pooled VICE, loads the party, and reads `$5700`-`$57FF` out of the running machine before and after `ADD CHARACTER TO PARTY`. That is what settled `#435 (A rename in Wish leaves the C64 name table holding the old name on Curse and Silver Blades, and nobody knows what reads it)`: `GEN` clears the block and refills it from the save disk's directory before every read, so a stale entry never reaches a screen. `--remove NAME` takes a character out of the party first, which makes the game write the character file the scan then finds; `--resave` takes `SAVE CURRENT GAME` at the end, which is how the buffer was caught being stored as though it were a record. Every image the game sees is the slot's own copy. |
| `c64outdoor.py` | Makes an engine-written C64 *Pool of Radiance* saved game standing on the overland travel grid, which none of the player's own twenty save disks is -- every one reads `$49E6` = 1, so until this there was nothing to drive the DOS converter's outdoor branch against. The C64 twin of `tools/dos/dosoutdoor.py` and the same seed-and-resave shape: one of the player's indoor disks is read (never written) and pointed at a travel window by `goldbox.dos_codec.apply_file_cache` and `apply_position` -- `#47 (Decode the travel grid's cache entries, so the wilderness can be retargeted too)`'s outdoor recipe, reused rather than copied -- VICE loads that seed, the party **walks** so the saved square is one the engine moved it to, and the game's own `ENCAMP > SAVE` writes the disk back. `--saves` takes more than one, walking between them. At every step it reads the live travel square, the frozen dungeon square, `$49E6`, the loaded-files cache and `$033D`, which is where the eight-way travel heading lives -- outside the `$4900`-`$64FF` a save images, which is why an outdoor conversion cannot carry a facing. |
| `c64portraitprobe.py` | Asks the running C64 game whether it draws a character's sheet portrait, and **which art it fetched**, without anybody having to squint at pixels: it reads the loaded-files cache at `$6E13` while the sheet is up, where slot 14 holds the resident `HEAD<xx>` and slot 13 the `BODY<xx>`. That is what settled `#57 (Carry the character portrait across ports)`'s import half. `--words 49FF=0x81` and `--portrait SLOT=HH/BB` patch the **staged copy** of the save disk, so one run differs from the last by one byte; `--poke 49EB=0` writes RAM just before `VIEW`, which is the only way to test a saved-game word the arriving area's script overwrites on load; `--prompt-side 3` answers the game's disk prompt with the side that carries every portrait, rather than the side it asks for. PORSAVE12 with `$49FF = $01` fetched nothing and drew a blank sheet; the same image with that one byte `$81` fetched `$08`/`$07` for BRUTUS and `$09`/`$02` for MALCYON and drew the faces, and a converted party staged with the six ids the patch would write fetched all six of its own, 6 of 6. |
| `c64recordoperandsweep.py` | Counts the absolute, absolute,X and absolute,Y 6502 operands that land in a window of the C64 character record (`$7C00` for Curse and Silver Blades, `$6B00` for Pool), per file, across one title's registered disks. Takes GAME (`curse`, `pool`, `ssb`) and hex LO and HI. A byte scan that does not follow the code. A measurement for #192 (Convert a Curse of the Azure Bonds DOS save into a C64 one, which the importer refuses today). Reads only. |
| `c64restinterrupt.py` | Says whether a C64 rest can be interrupted where the party is standing, and proves it in the running game -- the instrument behind `#250 (Does a C64 party resting in the Slums ever get interrupted without the murder flag?)`. `code` reads the gate out of the player's own disks (`CAMP $1E0F`, which skips the whole check when `$6DD2` is zero, and `DUNGEON $10A1`, which zeroes the pair and then runs the area script's entry 2) and then walks every area script's entry 2 **from entry 2**, so a conditional pair is reported as the values each arm reaches rather than whichever came first in address order: six of the thirty areas can never interrupt a rest and two always can. It also walks both arms of every conditional through the statements that leave no trace and reports the ones that arrive at the same single statement -- two of two in `ECL14`, none in the other twenty-nine, which is what tells a mistake from a design. `drive` claims a pool slot, checks the resident script against the file before believing anything, and counts passes, checks and interruptions with non-stopping VICE checkpoints while the party rests in two-hour blocks -- one check's worth when the pair is (24, 24) -- with the murder flag clear, with it set, and with it set and the chance held at zero so a check can never win. The rest duration is written into `CAMP`'s own `$2898`-`$289A` rather than driven with INCREASE, whose step grows while the key is held. Nothing is written to the player's disks. |
