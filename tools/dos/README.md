# dos

Scripts for the DOS ports: DOSBox and the drivers built on it, overlay and record readers, and the save and party tools.

| file | purpose |
|---|---|
| `daxls.py` | Lists, unpacks and renders the blocks of a DOS Gold Box `.DAX` container -- the command-line form of `goldbox.dos_savegame.dax_index`/`dax_unpack`, which every tool that wanted one block used to reach into by hand. The listing gives each block's id, offset, packed and raw sizes and, where the block is an image, its width and height and the nine unread header bytes; `--dump` writes one unpacked block to a file and `--png` draws an image block as EGA. An image block is recognised by the one test every such block in the game passes, its length being exactly `17 + rows * width / 2`. `docs/168-dos-dax-and-combat-icons.md` has the block layout. |
| `dosabilitypair.py` | Says which byte of a DOS ability pair is the score in force, which is what settled `#401 (Which byte of a DOS ability pair is the current score, now that the C64's two arrays are named)`: for strength through charisma the **lower** byte of the pair is the permanent score and the higher one is what is in force, and for the exceptional-strength percentile it is the other way round. `sites` is the evidence -- six instruction signatures matched in the shipped `GAME.OVR`, present in all five DOS engines that keep pairs and in none of Pool of Radiance, which keeps one copy of each ability and is the negative control. `census` counts the byte accesses that name each displacement, as a shape rather than a count of instructions. `stage` writes the two bytes of one pair **apart** (`--set PHILIPPE:str=18/9`) so that a boot can answer what no saved game can -- all 406 pairs this project can reach hold their two bytes equal -- and `read` prints every pair of every record. The player's archives are opened read only. `docs/204-the-dos-ability-pair.md` is the write-up. |
| `dosaddchar.py` | Drives DOS *Pool of Radiance*'s `ADD CHARACTER TO PARTY` and measures the duplicate test behind it: two `.CHA` files built by `goldbox.dos_codec.write` from different shipped records, renamed to the same name, offered to an empty party so capacity cannot be the cause, and differing in one byte -- `0x0AB`, the identity the engine compares after the name. `--ident 0` is refused and `--ident 0x42` is let in, which is what settled `#216 (Every converted DOS character carries the same identity byte at 0x0AB)`; `--writer` leaves the byte as the writer writes it today and is the run that says the fix works in the game. Ground truth is the engine's own `SAVE CURRENT GAME` into an unused slot and the `CHRDAT` files that appear on the host, never the screen. Two things it knows that the next driver of that menu will need: the arrow keys do nothing there (`Home`/`End` move the highlight, `N`/`P` turn the page, any other key picks), and an entry is starred once its file has been read, so the star is the proof that a refusal was a refusal rather than a mis-driven menu. |
| `dosarraywidth.py` | Reads how wide an array inside a DOS character record is straight out of the engine, with no emulator and no specimen. A record is reached through a far pointer, so a *0-based* array walk compiles to a byte counter compared against the array's **last index** and then `add di, ax` / `es:[di+<offset>]`: this scans an overlay for every `es`-prefixed access at a field's displacement, disassembles each with `capstone`, and tallies the `cmp byte [bp-n], imm` guards in the 90 bytes before it, stopping at a `retf`/`ret` so the tally cannot cross into a different subroutine. `--family` runs all four titles at once, which is the honest way to use it — the three whose widths were already measured act as controls, and a reading is only believable when they come out unchanged. It is what settled `#508 (A converted magic-user loses memorised spells on the way to DOS, because our table says a title has fewer slots than the engine gives it)`: Pool of Radiance's memorised list is **21 entries at `0x017`**, four loops bounding the index at `0x14`, where `goldbox/dos_port.py` declared 16 at `0x01C` and the five bytes in front had been named `gap_017`. Curse, Silver Blades and Pools of Darkness come back 84, 75 and 141, which is what those tables already said. `spells_castable_cleric`, `attack_forms` and `field_83_87` are settled as declared, per `#516 (Generate boundary characters and check every writer's field widths, since no real save reaches a limit and the corpus cannot find a wrong one)`'s slice 3. Its limits are `dosfieldrefs.py`'s: nothing checks that a match is an instruction rather than data, and **an empty result is evidence and not proof** — a big array is usually walked by adding the offset into a pointer first, which is why the spellbook gives no hits in any title, and a **1-based** `for i := 1 to N` loop (the compiler emits both) carries the offset one lower than the field's own, so this tool cannot see it at the field's own offset at all -- `dosrecordloops.py` reads that shape directly. Reads only. |
| `dosbox.py` | A driven DOS Gold Box session: DOSBox on a private X display, unattended. Input is XTEST through `xdotool` aimed at a window nobody else owns (there is no window manager under a bare `Xvfb`, so `windowactivate` fails and the keystroke is lost); output is a 320x200 capture that is the VGA framebuffer pixel for pixel; ground truth is the save file DOS writes. The window is chosen by `_NET_WM_PID` and then proved to have pixels in it, a display something already answers on is refused rather than shared, and a screenshot of one flat colour is refused by name (`#88 (tools/dos/dosbox.py can capture the wrong window, and then every screenshot is black)`). |
| `dosboxx.py` | The DOS debugger harness: `dosbox.py`'s session with the launch replaced by a DOSBox-X built `--enable-debug=heavy`, on a pty so its ncurses debugger has a terminal. Memory reads, `BPM` watchpoints, code breakpoints, registers, single-stepping and writes, over a log file — the DOS answer to VICE's binary monitor. Hides the four traps that cost an hour each: the 64K `MEMDUMPBIN` wrap, the spurious first `BPM` hit, the code breakpoint that logs nothing, and the 254-character command truncation. Displays :90-:105. |
| `dosbyteimm.py` | Which constants a DOS overlay ever stores into, or compares against, one character-record byte. `dosfieldrefs.py` counts the instructions that touch an offset and says which of them write; this says what value they write, which is what names a field. A byte the engine sets to `0Ah`, `0Ch` and `0FFh` is not a marching position, and one it sets to `0B2h` and `0B3h` and compares against `80h` and `7Fh` is a bitfield with a flag in the top bit -- both readings came out of it, for `#305 (Two DOS record bytes have one name from Pool of Radiance and another from the Curse decompilation)`. `--offset` names the byte. |
| `dosdis16.py` | A 16-bit listing of any window of a DOS Gold Box image, by file offset -- the general form of what `dualclassdos.py code` does at the one site it goes looking for. Backs up until a decode puts an instruction boundary on the offset asked for, and says so rather than printing an aligned-anywhere window when it cannot. `--strings` lists the printable runs matching a regex with their offsets, which is how the Silver Blades party-menu dispatcher was found from the string `Free training on` (`#234 (A dual-classed Curse or Silver Blades character converted to DOS loses the class he trained out of)`) |
| `dosdisk.py` | Builds a C64 save disk from a DOS save folder, owing nothing to another save -- the command-line form of what `File > Import` does after `#118 (Write a C64 save from nothing, so importing a DOS save needs no existing .d64)`. `goldbox.dos_codec.new_save` writes all 9216 bytes of `SAVEDGAME0` and `SAVEDGAME1` from two zeroed buffers and `save_disk` puts them on a `D64.blank()`; the two things no DOS save can supply, the composed combat icon and `ANIMATE00`, are read off the player's own `POOL` sides at run time and the tool refuses without them. `--sheet` prints the DOS party the way the C64's `VIEW` screen lays it out -- name, race, alignment, class, the six abilities, level, experience, hit points, armour class, THAC0 and money, with `armour_class` and `thac0_current` decoded through the family's `60 - value` -- which is the side of the `#119 (Play a converted DOS save in VICE, off a disk Wish built from nothing)` comparison a person reads against the running game. |
| `dosdropcensus.py` | Whether any DOS record on this machine sets a field the conversion cannot yet carry, asked as a question per column rather than as a byte partition: "is the second byte of an ability pair different from the first", "how many spell ids are in the memorised list", "is the druid slot array non-zero". It calls `dostailcensus.py`'s finder, so the corpus is the one `#235 (Two unattributed DOS byte ranges in the combat tail are dropped converting to C64, and nobody knows what they hold)` and `#224 (0x0B9 and 0x0BA are documented both as an NPC marker and as the dual-class slot)` were answered over, and it prints the provenance caution on every run because a reader who takes these counts for the game's behaviour has misread them. On Curse's 58 records five of the six columns `#192 (Convert a Curse of the Azure Bonds DOS save into a C64 one, which the importer refuses today)` step 0c asked about are empty -- 0 of 406 ability pairs differ, no druid slot and no fourth- or fifth-level slot is set anywhere, and the widest memorised list is 7 ids -- which is what says each of those carries needs a specimen made rather than found. |
| `dosencrecompute.py` | When the DOS engine rewrites a character's stored encumbrance, read from the shipped binaries, which no edited save can poison. `routine` finds the recompute function by its signature, `callers` says who calls it and who writes money, and `bags` lists every record carrying a bag of holding. It answers `#323 (The encumbrance identity does not survive the training fee, so failing it is not evidence of an edited record)` from code, where `tools/records/enccensus.py` answers it from records and `dosencsave.py` from a driven boot. |
| `dosencsave.py` | Which screen makes DOS Pool of Radiance rewrite a character's stored encumbrance, with the spoiled value written into the file **before the boot** so the engine actually reads it. `--rungs` re-runs `dostrainprobe.install`'s own gold arithmetic over the training-ladder specimens and `--boots` reads a driven run's `before/` and `after/` snapshots, both with no emulator; the driving mode boots once and takes up to three saves off one spoiled load -- a party-menu `SAVE CURRENT GAME`, a camp save, and a save after `VIEW` drew a sheet. Answers `#323 (The encumbrance identity does not survive the training fee, so failing it is not evidence of an edited record)`. |
| `dosencumbrance.py` | Weighs a DOS character against the encumbrance the record stores, printing both sides of `money + sum(weight x quantity)` coin by coin and item by item, so a discrepancy lands on a term instead of being argued about. `--census` sweeps every `.SAV` and `.CHA` on the machine, deduplicates on the record bytes together with its items', and reports how the discrepancy is distributed -- 264 distinct records on 2026-09-04, 214 balancing exactly, the six that miss by `+3` all Curse characters straight out of the Tilverton shop, and two Pool of Radiance dart-throwers short by exactly the darts their cached name has not caught up with. It is what turned `#225 (A shopped Curse character's stored encumbrance is three tenths above the sum)` from an anecdote about one character into a count, and what measured the four purchases behind `docs/125-bug-notes.md` N19. |
| `dosfieldrefs.py` | Scans a DOSBox-X memory image for every instruction that reaches a character-record offset through an `ES` far pointer, split into reads and writes, which is what stands in for a read watchpoint the debugger does not have. It is what answered `#69 (No WRITE_UNSOURCED zero has been tested during combat)` for `hands_used`: eight sites address `0x100` and exactly two write it, both inside the inventory recount, the first an immediate zero -- so the field is rebuilt before it is read and our zero cannot be believed as combat state. Its limits are in its own docstring and matter: a displacement match does not prove the pointer is a record, one image is one set of overlays, and **nothing checks that a match is an instruction rather than data**, so a count is an upper bound and a site is only worth believing when a `BPM` hit or a disassembly corroborates it. |
| `dosfightrun.py` | Drives a DOS Pool of Radiance fight to its end, and the capture run that made that possible. `capture` presses a ladder of keys at whatever is on the screen and logs every quarter second -- bar, status and whole-frame digests, a PNG the first time each command bar appears, and the save files either side -- which is how the digests in `PoolOfRadiance.COMBAT_BARS` were read and how `QUICK` was put to the test. `fight` is the driver those digests made possible. Ground truth is the save file: experience rising in `CHRDAT<slot><n>.SAV` says monsters were slain and so names the party as the killer, where hit points falling says only that the party was struck. The runs' output is kept at `cited/dosbox/p114/`; the tool writes under `<tmp>/wish/dosfightrun/`. |
| `dosfightwatch.py` | Watches a converted party's `WRITE_UNSOURCED` bytes through a DOS fight -- the measurement `#69 (No WRITE_UNSOURCED zero has been tested during combat)` asks for. `locate` converts a C64 save disk with `goldbox.dos_codec.new_dos_save`, boots DOSBox-X, walks until a wandering encounter stops the party, dumps a megabyte and finds each character's live record in it by matching the file it wrote; `watch` goes on to arm a `BPM` on every zeroed field, drive the fight, and log each write with the command bar that was on screen when it fired and the `CS:IP` that made it; `truth` has the game's own `ENCAMP > SAVE` author the same party first, so what the engine holds when a fight begins can be set beside what a conversion holds. There is no read watchpoint in DOSBox-X, so *when* the engine writes over our zero relative to the fight's phases is the measurement available. **The party has to be somewhere wandering encounters happen**: all but two of the player's save disks are in New Phlan, which has none. Output goes to the tool's scratch directory, or to `--out`; the run for the measurement is kept at `cited/69/`. |
| `dosframeaudit.py` | Counts the DOSBox-X frames that are not a clean 2x2 replication, which is the one measurement `#215 (Nothing checks that a frame halve() is about to halve was really line-doubled)` asks for before a uniformity check can be added to `dosboxx.halve()`. Boots one pooled instance, loads a slot, and takes several hundred **unhalved** captures -- `dosbox.Session.capture`, the frame `halve()` is handed -- turning the party between batches so the viewport is redrawing and a capture caught mid-redraw is in the sample rather than excluded from it. Reports how many frames had a ragged 2x2 block, how many blocks, and where the first few were. |
| `dosgnome.py` | Rolls a character in DOS Pool of Radiance's own CREATE NEW CHARACTER screens under DOSBox and dumps the `.SPC` effect records the engine writes for it; `--interactive` executes step lines appended to a command file, so one boot maps many menus. Wrote the gnome measurement in `#84 (Roll a gnome in DOS and read the two innate effect ids nobody has seen)` |
| `dositemcap.py` | Proves DOS Pool of Radiance's sixteen-item ceiling in the running game, for `#52 (File ▸ Import and File ▸ Export for every direction the library supports)`'s decision 13. Installs `WISH-SPEC-por-party-l1-intown` into a staged `SAVE`, gives characters 1..n item lists of whatever length is asked for -- copies of the game's own `Sling` template out of `ITEM1.DAX` block 53, with `item_count` and `encumbrance` written to match -- boots, loads the slot and then runs step lines appended to a command file, `dosgnome.py`'s vocabulary plus `@key`, which presses and shoots with **no** settle because the refusal message is on screen for about a tenth of a second and a `settle()` is guaranteed to miss it. The sling is chosen for weighing two tenths of a pound: the refusal routine shares one flag between the item count and `encumbrance + weight x quantity` against carrying capacity plus 1500, so a heavy inventory would prove nothing about the count. `--counts` is the whole experiment -- 2,15,16 gives the boundary (the same item accepted by the character holding fifteen and refused by the one holding sixteen), 16 alone shows `HALVE` missing from the item bar until one item is dropped, and 20 shows that the ceiling is on acquisition only. A character carrying nothing gets **no** `.ITM` file rather than an empty one (`goldbox.dos_codec.ITM_OMITTED_WHEN_EMPTY`): writing a zero-length one reproduces the phantom-item half of `#62 (A converted character who owns nothing gets a corrupt sheet, and DOS then invents a garbage item)` on a record the engine itself wrote. |
| `dosladder.py` | Climbs a DOS *Pool of Radiance* party a level at a time through the game's own four training schools -- clerics, magic users, fighters and thieves -- in one boot per level, keeping every record the trainer writes, for `#249 (Build a DOS party from creation and level it ourselves, so DOS measurements rest on records we watched being written)`. | `dosmodifyprobe.py` | Watches DOS *Pool of Radiance* write the treasure-share byte at record `0x085` by pressing KEEP, for `#304 (field_83_87 is written as a constant that the characters we rolled ourselves do not hold)`. | `dosnewsave.py` | Builds a DOS *Pool of Radiance* saved game from a C64 save disk with no template, boots it under DOSBox and reads the party off the game's own screens -- the acceptance check behind `#26 (Write a DOS save, not just read one)`, and the DOS-side twin of `dosdisk.py` and `tools/c64/savecheck.py`. `goldbox.dos_codec.new_dos_save` writes all 13137 bytes of `SAVGAM<slot>.DAT` and every `CHRDAT<slot><n>` beside it from 13137 zeroes, and the run is what turns the file's declared zeroes into measurements: the party loads, its sheet and item list are captured, `--steps` walks it (turning when a step is refused, fighting when something interrupts), and the game's own `ENCAMP > SAVE` writes the slot back so the resave can be diffed against what we wrote -- the engine's own rewrite being the oracle for which zeroed bytes it fills in for itself. | `dosoutdoor.py` | Makes an engine-written DOS *Pool of Radiance* saved game on the overland travel grid, which nobody's own save is: all three of Donald's are indoors, and the three made for `#50 (Lift the wilderness refusal from the DOS save converter)` and `#59 (Map the DOS saved game, not just the character record)` in 2026-08 lived in scratch (deleted) and are gone with the script that made them. | `dosptrfields.py` | Censuses the structure offsets reached through one global far pointer, which is how a DOS Gold Box heap block's field map is read without a symbol table.
