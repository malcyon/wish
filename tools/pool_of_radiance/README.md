# pool_of_radiance

Scripts for Pool of Radiance: driving fights and outdoor walks, and replaying a load failure.

| file | purpose |
|---|---|
| `attackwatch.py` | Presses the attack step next to an enemy in a driven fight and then sends nothing else, polling the screen and the target every quarter second for ten seconds and logging what the game does -- whether the attack resolves, how long it takes, and whether `MOVE LEFT` ever moves. Belongs to `#127 (A driven character stands next to an enemy and passes its turn instead of attacking)`. Takes an optional log name, save disk, time budget and pool slot; writes `<name>.jsonl` in the tool's scratch directory. It drives an emulator. |
| `defeatdrive.py` | Loses a Pool of Radiance fight on purpose and reads what the game prints, which no run had ever done: it boots a pool slot, walks into the slums ambush, sets **every** occupied roster slot's hit points to 1 through the monitor so the engine's own damage code writes the statuses, passes every turn, and then watches. It records three things a screenshot cannot carry -- every distinct screen with the readings that saw it, the **program counter** (`POST.COM $0957` is `JMP $0957`, so a PC that stays there is a locked machine), and the save disk's SHA-256 either side of the fight. `--knock` presses Return and space at the message once, to say whether a player can get past it. Output goes to `--out`, by default `<tmp>/wish/defeatdrive/<save-stem>`; the run behind the finding below is kept at `cited/128/`. It settled `#128 (Nothing has ever read what the game prints when the party loses a fight)`: `THE PARTY HAS LOST`, `$6DC7` = `$80`, all six characters `DYING`, the save untouched, and 66 of 66 PC readings at `$0957`. |
| `dirtenicon.py` | Inspects a Pool save for a uniquely identified joined DIRTEN with an entirely zero combat icon; `--out` creates a new repaired D64 without overwriting any file. Reads and cross-checks the native default from the player's `POOL3` option data and `POOL1` initialization seed, verifies that only the target icon changes, and prints source/output hashes. Uses `POR_DISKS`, then `automap.paths.find_disks()`. |
| `fightrun.py` | Drives one fight from a player's save, unattended: boot a pool slot, load the save, walk until something ambushes the party, and hand every command bar to `Session.melee_turn`. Writes one JSON line per turn and prints the only summary that says whether a fight was fought — per character, the turns taken, how many had an enemy in contact, and how many of those ended with a blow struck. Three copies of this were written into scratch for `#126 (The emulator harness cannot drive a fight, so no conversion has ever been proven in combat)`, `#127 (A driven character stands next to an enemy and passes its turn instead of attacking)` and `#165 (One character that cannot act takes every turn in a driven fight)` and thrown away with it; the data it produces goes to the temp directory, and the tool is kept. |
| `fleedrive.py` | Runs a *Pool of Radiance* party away from a fight and reads what the game prints, for `#445 (The game's third fight outcome, THE PARTY RUNS AWAY, has never been seen on a screen)`. `code` needs no emulator: it reads each C64 title's `POST.COM` off the player's disks and prints the three end-of-fight lines and the branch that picks the fleeing one. `drive` uses the game's own FLEE by walking each character off the edge of the combat map, and once the game has recorded a flight it puts whoever is still standing on one hit point and passes their turns until the fight ends. |
| `koboldnpc.py` | Watches the Kobold Caves' exit take an NPC out of the party, and watches a fast travel not take her, for `#180 (What the Kobold Caves exit does to an NPC in the party is not understood, and Fast Travel skips it)`. Two plans boot the same save disk on a pool slot and end in area 27, so the only thing that differs between the capture sets is how the party left: `walk` steps south through the exit's own script, `warp` enters the new area the way Fast Travel does. Each capture is the eight master slots' names and roster status plus a screenshot, written to `--out`, by default the tool's scratch directory; an earlier run is kept at `cited/180/`. |
| `loadfailurereplay.py` | A VICE driver that fakes the hardware state of a load failure and confirms that the C64 vectors and BASIC interpreter match the exact output of the bug's screenshots. |
| `monstermsg.py` | What the game prints when a **monster** acts (`#350 (The Messages window logs the party's attacks and dice but nothing a monster does)`): `table` decodes `COMBAT`'s 64 messages out of `SPELLN00`'s pointer table, `sites` finds every place the overlay prints one and the index it used, `replay` runs a recorded fight through `automap/combatlog.py` with no emulator, and `fight` drives a slums ambush and polls the message panel at the 200 ms the Messages window itself ticks at, recording each message with the acting combatant `$A4F4`, the dice, and the names `combat.read_battle` gives. `--delay` pokes the game's own combat speed `$49FC`, which is what `#425 (The Messages window logs a quarter of a fight when the player turns the game's combat speed up)` measures. |
| `movekeysweep.py` | At a live MOVE sub-bar in a fight, presses every candidate key (the eight steps, `KP_5`, `KP_0`, space) and logs one JSON line per press: what was on the destination square, whether the character moved, what the bar said before and after, and whether the target lost hit points. It answers whether a step into an occupied square is refused or `KP_1` is dead, for `#127 (A driven character stands next to an enemy and passes its turn instead of attacking)`. Takes an optional log name, save disk, time budget and pool slot; writes `<name>.jsonl` in the tool's scratch directory. It drives an emulator. |
| `ohlowatch.py` | Drives Ohlo's potion errand in the running game and watches the Quest Log row follow it, which is the emulator half of `#158 (Track the quests the game itself forgets, starting with Ohlo's potion)`'s feature-flag removal condition. It boots a save with the party in the Slums, walks on to the booth at `GEO14` (15,12) and then on to Ohlo's own block, and renders `QuestLogPanel` offscreen from the **live** `$4900`-`$64FF` read -- the same block `automap/window.py`'s `_refresh_roster` hands the panel -- at each stage, so the chain from the engine's own `SAVE 250, [$4A81]` to the words on the row is one measurement rather than three. `$4A81` is sampled every 0.4 s, which is how the 22 s and 49 s the two visits took are numbers and not guesses. **None of the game's words are in this file**: the menu options, the prompt and the word the booth wants are unpacked from `ECL14` on the player's own disk at run time -- 6-bit packed, four characters to three bytes -- and the log says "option 3 of 3". `rows` is the half with no emulator in it, and renders the panel from any captured window. Two things it had to learn the hard way: `Session.walk_one` cannot verify a step in the Slums, whose status line carries no coordinates, and `$4A80` has to be held at its own cap of 15 or a wandering fight arrives on the step into the booth. |
| `outdoorstep.py` | Takes one compass digit at a time on Pool of Radiance's travel grid and prints **row 24 verbatim at every stage** -- before `MOVE`, after `MOVE` and after the key -- beside `$49C3`/`$49C4`, `$49C0`-`$49C2`, `$49E6`, the clock and the area, with a screenshot for each. `outdoorwalk.py` photographs each press and answers *which* digit went where; this answers *why a step was refused*, which a bare `moved=False` had been conflating with three different things: the square refused the party, the driver never found the movement prompt, or the key went somewhere the game was not reading. It is what settled `#382 (An outdoor Pool of Radiance party's compass step is refused, and the retry cannot find the movement prompt afterwards)` -- on the square an Amiga party sails to, selecting `MOVE` puts up `TAKE BOAT STAY` and the picture of the boat rather than `1-8, RETURN OR BUTTON`, so a driver that knows only those two waits out its timeout in front of a game that is asking it a question. `--boat STAY` declines the passage and is the default, because `TAKE` sails the party back to New Phlan and destroys the thing a step measures. Each digit is tried by XTEST and then through the KERNAL buffer, since a title that reads only one of the two looks exactly like a party hemmed in (`#192 (Convert a Curse of the Azure Bonds DOS save into a C64 one, which the importer refuses today)`, `#360 (The session driver will not walk a Curse or Silver Blades party in a dungeon, because it reads Pool of Radiance's indoors flag)`). `--resave` has the engine's own `ENCAMP ▸ SAVE` write the party back and copies that disk out. Output goes to `--out`, under the temp directory; the player's disks are read only. |
| `outdoorwalk.py` | Walks a party on the C64 travel grid one key at a time, photographing the frame before and after each press, which is what to reach for when the question is *which* digit went where. It reads `$49C3`/`$49C4` through the binary monitor rather than the status line -- outdoors that line reads `OUTDOORS 22:02 7,28`, with the word where the facing letter goes, and it lags the step by about a second -- and polls rather than sleeping, since an overland step is about twelve hours of game time. **The overland move bar is `1-8, RETURN OR BUTTON`**, the compass clockwise from north (1 N, 3 E, 5 S, 7 W), not the dungeon's `I J K M`. It is what proved `#50 (Lift the wilderness refusal from the DOS save converter)`'s converted overland party takes a step, and where `#189 (The emulator driver cannot move a party on the travel grid, and reads its facing out of the word OUTDOORS)`'s fix was lifted from: `tools/c64/session.py` knows all of this now, so `tools/c64/savecheck.py --walk` walks an outdoor party too and this tool is no longer the only way to see one. |
| `porattract.py` | Runs Pool of Radiance's opening attract loop in a pooled VICE and watches for a stall -- the control for `#286 (Pool of Radiance on the C64 Ultimate sometimes hangs on a disk load) (Pool of Radiance on the C64 Ultimate sometimes hangs on a disk load)`, where the same loop stopped three times in three runs on the hardware. Boots `POOL1.D64`, answers `DISABLE FASTLOADER (Y/N) ?` and then sends nothing at all, because leaving the `PLAY GAME` menu alone is what starts the demo. Samples the **program counter** as well as the screen and the jiffy clock, which is the one thing the Ultimate cannot report, and dumps the registers, the stack page, both CIA ports and the bytes around the program counter when it stops. **Opens one monitor connection per sample**: a connection held across the loop stops the emulator for as long as it is open, which on this tool's first run froze the machine and then reported it as stalled. |
| `slumsquitprobe.py` | Drives one Slums ambush in a pool slot with the shipped `melee_turn` and, the first two times a sub-bar has no GUARD, presses QUIT instead, logging the mode byte, the acting index at `$A4F4` and rows 22-24 every 0.4 s, plus whether each character took MOVE that turn. Takes NAME, SAVE, BUDGET and SLOT; writes `<name>.jsonl` in the tool's scratch directory. Boots VICE. For #165 (One character that cannot act takes every turn in a driven fight). |
| `sokolarrivalcheck.py` | Claims a pool slot, stages the Pool disks and a save that arrives at Sokol Keep (the boat scene) into it, boots, loads, begins adventuring, prints each step's result and the status, and screenshots where it ended up: the live half of `#182 (A driven save that arrives on a picture is reported as a failed load)`, whose offline half is `tests/test_arrivalscene.py`. Takes the save as its argument. Claims a slot and boots an emulator. |
| `worldregisters.py` | Reads the chips while a party stands on Pool of Radiance's travel grid -- measurement B of [`docs/217-drawing-the-wilderness.md`](../../docs/217-drawing-the-wilderness.md), and everything the wilderness renderer needs that no file on the disks can say. It boots one outdoor save the way `tools/c64/c64outdoor.py` does (pool slot, staged copies of the player's disks, `Session`) and then reads instead of writing: `$D011`/`$D016`/`$D018`/`$DD00` for the mode and the character base, `$D020`-`$D023` for the shared colours, the screen matrix and `$D800` colour RAM, `$037E` the camera, `$6E13`-`$6E2B` and `$49C5` the live loaded-files cache, and `$8C00` the resident window. **The pane is found rather than assumed**: every 3 × 3 block of screen codes is looked up in a table of the window's own 120 tiles, so the view's size, its position on the screen and which grid squares are in it all come out of the match with no camera hypothesis in front of them. `--compass` presses each of `1`-`8` and reads `$033D` around it. Nothing is written to the player's disks. |
| `worldtiles.py` | Draws Pool of Radiance's 120 wilderness tile pictures the way the C64 draws them, off the player's own disks -- measurement A of [`docs/217-drawing-the-wilderness.md`](../../docs/217-drawing-the-wilderness.md). `goldbox/world.py` reads a `SQRDATA0n` tile as nine screen codes and nine colour attributes; this adds the three things that turn those into pixels: the glyphs out of `SECSET04`/`05`/`06` (glyph = screen code − `$40`), bit 3 of an attribute selecting a C64 multicolour cell over a hi-res one, and the three colours a multicolour cell shares with the whole screen, which are in `$D021`-`$D023` and in no file -- read off the chip by `worldregisters.py` as black, light grey and green. `sheet` writes one labelled PNG a window with each tile's index and how many grid squares use it, `view X Y` the game's own 5 × 5 pane around a square, `codes X Y` the screen codes and attributes that pane puts on the screen, and `census` the tile and attribute-nibble counts. The pictures are the game's art and go under `--out` (the tool's scratch directory by default); they are never committed. |
